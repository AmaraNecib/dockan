Judgement calls (baseline smells, not violations):

- **Two near-identical reads (`returnsList` vs `returnsForInvoice`).**
  Deliberate: one is the paginated review screen, the other the money-adjacent
  form read that must be complete. The design docs name the split; collapsing
  them would reintroduce the truncation bug.

  not page, so a total would be unused (avoiding speculative generality). The
  unpaginated `itemsAll` read follows the same shape.
- The panel still derives `priorByLine` client-side from the complete list
  rather than a dedicated server aggregate. This mirrors the api's
  `returnedByLine` map from every-status rows (documented in `invoice.tsx`), so
  the preview and the server cap agree; a server aggregate was not needed.
