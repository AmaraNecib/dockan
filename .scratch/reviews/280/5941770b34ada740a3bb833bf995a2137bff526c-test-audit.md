## The two 🔴

### R1 — the AAD-binding test passes against the pre-PR implementation

`apps/api/src/db/encrypted-connection.test.ts:419` "binds the stamp into the AAD, so a swapped stamp fails decryption" flips one byte at offset `VAULT_SNAPSHOT_MAGIC.length + 2` = 10 and expects `VaultCorruptionError`.

- Post-PR, offset 10 is the first stamp byte, so the failure can only come from the AAD.
- Pre-PR the envelope is `magic ‖ 1 ‖ sealed`, and `sealed` starts at index 9 with a 12-byte nonce (`crypto.ts:20 NONCE_BYTES = 12`). Index 10 is **inside the nonce**, so the GCM tag fails on the body instead and the same assertion passes.

The test proves "a corrupted byte is refused", which was already true. The tamper-evidence claim the whole design rests on has **no discriminating test**.

Fix: swap the whole stamp field and prove the sealed body is byte-identical, so only the AAD can explain the failure.

```ts
const before = fs.readFileSync(snapshotPath());
const fence = readSnapshotFence(before)!; // undefined pre-PR -> the test reds
const after = Buffer.from(before);
Buffer.from("b".repeat(32), "utf8").copy(after, VAULT_SNAPSHOT_MAGIC.length + 2);
expect(after.subarray(fence.bodyOffset)).toEqual(before.subarray(fence.bodyOffset)); // body untouched
fs.writeFileSync(snapshotPath(), after);
expect(() => createEncryptedConnection({ vaultId, masterKey, snapshotPath: snapshotPath() })).toThrow(VaultCorruptionError);
```

### R2 — the production wiring is untested; the fence can be switched off and every test stays green

The stamp reaches a connection in production only through `apps/api/src/main.ts:251-254` → `apps/api/src/db/vault-store.ts:39`. All 24 new tests call `createEncryptedConnection` directly; `openVaultStore` is exercised in `apps/api/src/lib/vault/gate.test.ts:134` and `apps/api/src/store/encrypted-store.test.ts:77`, **neither of which passes a `writeStamp`**. The new `logger` pass-through (`vault-store.ts:42`) is equally unexercised.

Concrete trigger: delete `vault-store.ts:39`. Production then writes legacy v1 envelopes forever — the fence is inert — and every test in the repository still passes. The design doc calls the unfenced path "the regression guard" (`.scratch/implementation/280-design.md`), which is exactly backwards for a High-assurance feature: the unfenced path is guarded, the fenced one is not.

Fix: one test that calls `openVaultStore({ …, writeStamp: () => tokenA, logger })` and asserts the envelope on disk carries the stamp, and one that asserts `main.ts`'s `writeStamp` closure returns `vaultLock.currentOwner().token` and throws when there is no lock.

### Assertion weaknesses inside otherwise sound tests

- `:625` `expect(fs.readFileSync(snapshotPath()).equals(written)).toBe(false)` is satisfied by **any** change, including a truncated or corrupt envelope. Use `expect(diskFence()?.stamp).toBe(tokenA)` — the sibling tests already do.
- `:343-344` "detects a former holder's snapshot … and rewrites it" asserts the stamp but not the content: a fence-repair path that re-sealed an **empty** image would pass, and the former holder's `shared` row would be silently gone. The sibling tests assert rows after the rewrite (`:363`, `:412`); this one does not.
