### 1 — The report and the design doc quote the run the head commit says proved nothing (severity 5)

`.scratch/implementation/295-report.md:25` quotes the spec's own output:

```
#295 measurement: converged in 4963ms; reader visibility=visible, focus events=0, visibility flips=0
```

and `:28-33` concludes: "The reader tab never flipped to visible … was never reloaded, was never clicked, and issued no mutation — so the bounded tick **was the only refetch trigger left** that could have carried the change."

Head commit `7998a8d`'s own message says the opposite about exactly that run:

> "The headless runner never hides a tab, so the reader reported `visible` for the whole run — and TanStack v5's focus manager reads document.visibilityState, so the interval fired with or without refetchIntervalInBackground. **The spec was green with the flag deleted**, and the ticket's central claim … was pinned only as an option object."

So the report's headline evidence is the run in which the focus path was *not* excluded, and the claim it draws from it was false at the time it was written. `git show 7998a8d -- .scratch/implementation/295-report.md` is empty: the report was not touched by the commit that invalidated it.

Same for the design doc's risk bullet, `.scratch/implementation/295-design.md:124-126`:

> "**The headless e2e never hides a tab.** The reader reports `visible` for the whole run, so the hidden-tab branch of `refetchIntervalInBackground` is not exercised there"

At head, `tests/e2e/client-freshness.spec.ts:133` does `Object.defineProperty(document, "visibilityState", { get: () => "hidden" })`, so the hidden branch **is** exercised and the bullet is now the opposite of the truth.

The spec is fixed; the two documents that travel with the branch still carry the pre-fix claim. Fix: re-quote the measurement from a head run (`reader visibility=hidden`) and rewrite the doc bullet to say the reader fakes a hidden document.

### 2 — The milestone's write budget is now spent 12× faster (severity 4)

`apps/web/src/pages/dashboard.tsx:28` — `const REFRESH_MS = HOT_COUNTER_REFETCH_MS;` (was `60_000`).
`apps/web/src/pages/dashboard.tsx:96-101` — the `onboardingProgress` query now carries `...hotCounterRefresh(refreshMs)` → `refetchInterval: 5000`.
`apps/web/src/pages/dashboard.tsx:108-115` — the effect increments `completionAttempts.current` on every `progress.dataUpdatedAt` change and calls `recordCompletion.mutate(undefined)`; `MAX_COMPLETION_ATTEMPTS = 5` (`:31`), the mutation carries `retry: 2` (`:84`).

Trigger: the four onboarding records exist (so `complete` is true), the reads succeed, and `onboardingComplete` keeps failing — a write-path validation error, or a partial outage. Each successful poll of `onboardingProgress` bumps `dataUpdatedAt`, so the effect fires every 5s: five ticks, ~25 seconds, budget gone, milestone never recorded, checklist never hides. Before this change the same five attempts lasted five minutes (5 × 60s). `onSuccess` resets the counter (`:89`), so only a failing write burns it.

The checklist is not a hot counter — it is a query whose completion *writes*. It should keep its own bound, or the budget should be time-based rather than count-based.

### 3 — A blank reason and no reason are two different identities (severity 3)

`apps/api/src/rpc/router.ts:691` — `reason: input.reason ?? null`. `??` catches `null`/`undefined` only, so `""` survives as `""`. The contract allows it: `packages/contracts/src/core.ts:1403` — `reason: z.string().trim().optional()` (no `.min(1)`). The seam stores what it is given (`stock-posting.ts:160`, `spec.reason ?? null`).

`apps/api/src/lib/stock-adjustment.ts:128` — `if (request.reason !== recorded.reason) return false;` is a strict comparison, so `""` never matches `null`.

Trigger, on one item, inside the 10s window:

1. `stockAddManual({itemId: I, delta: 5, unitCost: 100})` → recorded reason `null`.
2. `stockAddManual({itemId: I, delta: 5, unitCost: 100, reason: ""})` → request reason `""` ≠ recorded `null` → **no match** → a second movement is written and the stock moves twice for one intention.

The mirror order (`reason: ""` first, no reason second) fails the same way. The web never sends `""` — `apps/web/src/pages/stock.tsx:117` sends `reason === "" ? undefined : reason` — so the shipped flow is safe; the guard, though, is an API-level promise and the contract accepts the input. Fix: normalise a blank reason to `null` on the way in, the way the supplier path already does at `router.ts:1713` (`input.reason == null || input.reason.trim() === "" ? null : input.reason.trim()`). The inconsistency is inside one file.

### 4 — The effective window is 9–10s, and the doc says 10s (severity 3)

`stock-adjustment.ts:44` — `REPEAT_WINDOW_MS = 10_000`. `stock-adjustment.ts:80-84` — `repeatCutoff` = `localDateTime(now - 10s)`, truncated to the second. `drizzle-store.ts:89` — `createdAt` is the same one-second stamp; `drizzle-store.ts:1617` — the window read is `gt(createdAt, recordedAfter)`, exclusive.

Trigger: a movement recorded 9.4s before the request. `now = 12:00:30.000` → cutoff `"12:00:20"`; the movement's `createdAt` = `"12:00:20"` (truncated from `12:00:20.600`); `"12:00:20" > "12:00:20"` is false → the row is outside the window → the repeat is not caught. The effective window is **(9s, 10s]**, not 10s. The store test (`stock-ledger-store.test.ts:130-160`) pins the *store's* edge, not the guard's effective one. Immaterial for a double-click; material to the number the code and the doc advertise.

### 5 — "a background tab still polls" is bounded by the browser (severity 3)

`apps/web/src/lib/freshness.ts:53-55` and the design doc's risk bullet promise that a hidden tab keeps reading. A window that is minimized, or a tab in the background of its own window, reports `document.visibilityState === "hidden"`; Chrome throttles a hidden page's timers (to one check per minute after five minutes hidden) and then freezes the page. The 5s tick stops, and that window stays stale until the owner brings it back.

The ticket's v1 shape is unaffected — two *visible* windows side by side are not throttled, and the visible-but-unfocused case is exactly what the tick was built for. The claim in the comment is just wider than the guarantee.

### 6-8 — Nits

- The guard throws before the seam validates (`router.ts:678-700`), so a repeat of an action that would have failed for another reason reports the duplicate: post `{delta: -6}` twice on an item holding 10 → the second is refused as `STOCK_ADJUSTMENT_DUPLICATE`, and the advice ("change the reason") walks the owner into `STOCK_NEGATIVE` one step later.
- `pending-returns.ts:12` — `PENDING_RETURNS_REFRESH_MS = 60_000` survives as a default nobody uses: `app-shell.tsx:143` and `dashboard.tsx:59` both pass 5s.

## The defender's case, at this head

- **D1 — the tick is the right shape for v1 (confidence 9/10).** `main.tsx` builds a bare `QueryClient()`, so `refetchOnWindowFocus: true` / `staleTime: 0` apply: the window the owner *clicks into* catches up by itself. The unfocused window is the uncovered case, and a bounded tick is the cheapest honest answer — no transport, no server surface, no second implementation for the desktop sidecar. Kept.
- **D2 — the identity is now sound (confidence 9/10).** The request leads, and the two excluded fields are excluded for the right reason. The derived cost: the seam derives an inflow's cost as `spec.unitCost ?? cache.costPrice` (`stock-posting.ts:150-155`) with `cache.costPrice` seeded from the same item row the guard reads (`stock-posting.ts:118-120`, `router.ts:690`), so `expressUnitCost(…, item.costPrice)` tracks the seam exactly. The server-stamped date: `spec.occurredAt ?? localDateTime()` (`stock-posting.ts:145-148`) — two identical requests differ on it, so it must stay out, and the guard keeps it out only when the request did not express one.
- **D3 — the write lock comes first (confidence 9/10).** `router.ts:672` posts inside `withTransactionImmediate` → `BEGIN IMMEDIATE` (`drizzle-store.ts:791`). A deferred transaction would let a second writer's read land on a stale snapshot; this one cannot. The concurrent-post case is real: both writers serialise on one connection, the first commits, the second reads the committed row and refuses.
- **D4 — the e2e now genuinely proves the background flag (confidence 8/10).** The reader fakes `document.visibilityState = "hidden"` (`client-freshness.spec.ts:133`); query-core 5.101.x's `focusManager.isFocused()` returns `document.visibilityState !== "hidden"` when no boolean was set, so with the fake the interval's `refetchIntervalInBackground || focusManager.isFocused()` is false without the flag — the reader would never converge. That matches the head commit's ablation (`refetchIntervalInBackground: false` → 1 failed). I read 5.101.2's build; the lockfile pins 5.101.4 (`bun.lock:470`) and I could not read those bytes, so 8 rather than 10.
- **D5 — the guard compares every row in the window (confidence 10/10).** `drizzle-store.ts:1609-1618` is a windowed read, and `router.ts:697-700` compares the request against *every* row it returns, not the newest. The intervening-movement hole from the first round is closed.
- **D6 — criterion 4 holds (confidence 10/10).** `packages/contracts/**` is untouched in the diff; the new store read is internal to the api; the web changes are query options and a constant; no package, no `bun add`, no port beyond loopback.
