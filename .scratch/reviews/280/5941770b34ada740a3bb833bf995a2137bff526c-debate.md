## Verdict

No P1. The fence itself holds: no stale write is ever recorded durable, the AAD freeze is byte-identical to the released bytes, and every objection from the previous round at `a57f450` is closed at this head. What is not ready is the **reporting layer around it**. The one event code the PR adds for the diagnosis fires on every ordinary boot, is silent at the two places where a foreign overwrite is actually caught, and every non-mine outcome — including a plain unreadable prefix — reaches the owner as "another writer replaced your snapshot" before the process is killed. Five P2s, all cheap to fix in code or prose; none needs a redesign.

## What changed since the prior round at `a57f450`

All seven of the previous findings are closed at this head, verified line by line: the at-open foreign stamp now logs (`encrypted-connection.ts:261`), the false "useless to forge" docstring is rewritten (`format.ts:262`), the `close()` key/handle leak on a refusing checkpoint is fixed by the `try/finally` (`:440`), `readDiskFence` now distinguishes three outcomes (`:296`), the laundering cost is written into the design record, and the checkpoint-path injection test, the overwrite-war exhaustion test and the open-time surfacing test all exist. ### 1. The signal fires on 100% of boots (P2, score 6)

`lock.ts:384` mints the token per acquisition — `token: randomBytes(16).toString("hex")` inside `acquireVaultLock` — so no two process lifetimes share one. `main.ts:251` stamps that token into every envelope, and `encrypted-connection.ts:233` reads it once. The bytes on disk after any clean shutdown therefore carry the **previous** process's token, and `fenceSatisfied = opened.stamp === connectionStamp` (`:255`) is false on every single launch after the first.

Trigger: start the app, let it write a snapshot, quit, relaunch → `openSnapshot` returns `stamp = T_prev`, `connectionStamp = T_new` → `fenceSatisfied = false` → `logger.warn("VAULT_SNAPSHOT_FENCE_FOREIGN", "the snapshot on disk is stamped by a former holder: …")` (`:261`).

The design record calls this "a load-bearing signal, since these bytes were writable by a holder that is no longer the holder" (`.scratch/implementation/280-design.md:88`). In production **every** previous holder is a former holder, so the event carries no information about the case it was built for. The badge `لقطة من كاتب سابق` (`apps/web/src/lib/i18n.ts:148`) is factually right but arrives as a `warn` on every launch, which trains the owner to ignore the one row that would matter.

The defender agrees independently (limit 2 of the accepted limits): "Read the event as 'these bytes were not written by this process' — **not** as 'data was lost'. A reader who alerts on it as an incident will get one per restart."

Two things are **not** consequences of this, checked and dismissed: the snapshot is not re-written more often because of it (`drizzle-store.ts:1263` already does `markDirty()` + `persistIfDirty()` on every boot), and the data is not lost by it (the boot write re-seals the holder's own in-memory image).

Direction: the routine case must stop being a warning — either emit it at `info`, or re-word the code and badge so it reads as "unverified currency", not "another writer". The design record's "load-bearing signal" sentence is the claim to fix. Making the event *discriminating* needs more than wording: the stamp carries no version to compare (the code says so at `:258`), so a zombie is indistinguishable from an ordinary restart. That needs a holder epoch in the fence — a format change, and therefore an issue rather than this PR.

### 2. The diagnosis never reaches the log where the race is caught (P2, score 6)

`VAULT_SNAPSHOT_FENCE_FOREIGN` is emitted in exactly one place: at open (`:261`). The two sites that implement the issue's actual window never log it. `grep -n "logger" apps/api/src/db/encrypted-connection.ts` returns three hits: the type at `:109`, the at-open warn at `:261`, and the `UNREADABLE` warn at `:337`.

Trigger: a zombie renames its envelope between our `await writeFileAtomic(...)` (`:371`) and our re-read (`:383`) → `diskFenceIsMine()` is false → `lastError = new Error("the snapshot was replaced by another writer's envelope")` (`:384`) → `continue` → three attempts → `SnapshotPersistenceError` (`:393`) → `drizzle-store.ts:767` logs `SNAPSHOT_PERSIST_FAILED` / "committed data could not be written to the encrypted snapshot" → `main.ts:274` logs "FATAL: encrypted snapshot could not be written; exiting to avoid divergence" and calls `process.exit(1)`.

Two defects in one line. The headline is false — the write landed three times; the file was overwritten by somebody else, the disk did not fail. And the event code the PR added for this exact diagnosis is absent from the log row. The owner is told the disk failed to write when the disk was stolen.

Direction: emit `VAULT_SNAPSHOT_FENCE_FOREIGN` at `:383` and `:430`, and give `SnapshotPersistenceError` a distinguishable cause so `main.ts:274` can say "another writer replaced the snapshot" instead of "could not be written". The code already knows the graceful shape of this condition: `main.ts:267` handles `VaultLockLostError` ("another copy owns the folder") by serving the in-use refusal instead of dying. Whether the fence refusal deserves the same treatment is the owner's call — a contested folder may legitimately be fail-stop — but the message must stop blaming the disk.

### 3. A read failure is reported as an attack, and it kills the process (P2, score 6)

`readDiskFence` (`:296`) is careful: it distinguishes `absent` (no file), `undecidable` (bytes that are not a fence this build knows) and `unreadable` (an I/O failure). `diskFenceIsMine` (`:326`) then collapses all three into a single `false`, and the post-write branch hardcodes the cause for every one of them: `new Error("the snapshot was replaced by another writer's envelope")` (`:384`), same string at the checkpoint refusal (`:431`).

Trigger: the 74-byte prefix read fails with `EBUSY` / `EACCES` / `EMFILE` — Windows rename contention, a removable FAT volume, fd exhaustion → both attempts fail → `diskFenceIsMine()` returns false → the write is redone → the same read fails → three full serialize+encrypt+rename cycles → `SnapshotPersistenceError` → `process.exit(1)`.

The bytes were written. The file is on disk. The process dies, and the last line the owner sees blames another writer.

The `absent` case is worse than `unreadable`: it reaches `false` on the first attempt, with **no log line at all** — the `UNREADABLE` warn at `:337` only fires when both attempts come back `unreadable`. A vanished snapshot file is reported as "another writer's envelope" with zero supporting evidence in the log.

The defender's own summary of this design — "the failure mode of that choice is a redundant rewrite" (defense 8) — is wrong for the post-write path. The failure mode is a fatal exit after three redundant rewrites. The defence holds for the *pre-write* call at `:355` (where a `false` just means "write it"); it does not hold at `:383`, where `false` means "the version you are about to call durable is not on disk" and the code answers by rewriting and then dying.

Direction: carry the outcome through to the error, and separate "the file is not mine" from "the file could not be read" from "the file is gone". A read failure must not be a `process.exit(1)`.

### 4. The backup path never consults the fence (P2, score 5)

`writeBackupTo` (`:485`) calls `connection.checkpoint()` (which does check the fence at `:430`), then reads the file back in a **separate syscall** (`:489`) and bundles whatever bytes are there. A rename landing between the two puts the zombie's older image into today's backup.

The validator cannot catch it: `validateSnapshotFile` (`:455`) derives the AAD from the envelope's own stamp field, so a foreign-stamped envelope decrypts cleanly, and the only other check is `quick_check` (`:474`), which a coherent-but-stale image passes. The owner is told today's backup is valid while the acknowledged transactions are missing from it — the exact loss the backup exists to prevent.

Direction: `readSnapshotFence(snapshot)` on the bytes actually captured, and refuse the bundle when the stamp is not this holder's. This is one call on an in-memory buffer.

### 5. The retry that exists for a transient error has no delay (P3, score 4)

`FENCE_READ_ATTEMPTS = 2` (`:143`) and the loop at `:328` asks twice back to back — two `openSync` calls microseconds apart against the same handle state. The docstring's claim that "one retry absorbs a transient EBUSY" does not hold for a Windows `ERROR_SHARING_VIOLATION` that clears in 30 ms, which is the timescale of the thing it is aimed at.

The codebase already knows the right shape. The write path waits `WRITE_RETRY_DELAY_MS = 50` between attempts (`:374`); `lock.ts:447` waits `DEFAULT_TRANSIENT_READ_RETRIES = 10` × `DEFAULT_TRANSIENT_READ_RETRY_DELAY_MS = 100` for the same errno class. The fence path is the one place that reads a possibly-busy file with no patience at all.

Direction: use the write path's 50 ms delay. This is the cheapest mitigation for finding 3's fatality: with the delay, the common transient clears and the process never reaches the fatal branch.

### 6. A callback that is called once (P3, score 4)

`writeStamp` is documented as "The current holder's single-writer lock token, stamped into every snapshot this connection writes" (`:93`) and supplied as a function (`:96`), which reads as "ask at write time". It is called exactly once, at construction (`:233`), and cached for the connection's life. The defender defends the substance correctly — the token is stable for the lock's life (`lock.ts:245` preserves it across heartbeats), and mid-life loss is the write guard's job.

The residual is a contract mismatch, and #287 is the obvious place it bites: if the heartbeat work ever rotates the token, every envelope carries a token no holder will recognise, and every boot becomes a rewrite plus a foreign-stamp warning, with no error anywhere. The callback shape hides that trap.

Direction: say "read once at open" in the option's doc, and put the "the token must not rotate while a connection is open" constraint in #287's brief.

### 7. Two diagnoses, one code (P3, score 3)

`:261` emits `VAULT_SNAPSHOT_FENCE_FOREIGN` for a legacy v1 envelope with no stamp at all and for a genuinely foreign stamp, with only the message text differing. A v1 file is not "foreign" — it is the documented pre-upgrade format that `docs/one-build-and-recovery.md` now explains at length. Filtering the diagnostics log by code cannot tell "another writer's bytes" from "this vault has not been written since the upgrade".

Direction: a third code (e.g. `VAULT_SNAPSHOT_FENCE_UNSTAMPED`) with its Arabic badge. The two source-scan tests (`apps/api/src/lib/log-events.test.ts`, `apps/web/src/lib/log-copy.test.ts`) enforce both sides of that change, so the shape is already known.

### 8. The cost line understates the dirty path (P3, score 2)

The design's cost list says "A read-back per write adds a 74-byte read" and "A read per `persistIfDirty` when clean" (`280-design.md:128`). A dirty persist actually reads the fence three times: `persistIfDirty` (`:406`) → `persistNow`'s own check (`:355`) → the post-write re-read (`:383`). The second read is not waste — it re-checks after the queue delay, and the third is the feature — but the cost line describes neither. Fix the line; the code is right.

## What the defender holds, and the synthesis accepted

The defender's load-bearing defence — that the reader must derive the AAD from the envelope's own stamp rather than from its own token — is correct and is what makes the whole design possible (defense 2). Because the token is regenerated per acquisition, deriving the AAD from the holder's own token would make every restart an undecryptable vault, and "these bytes are not mine" would be indistinguishable from "this file is corrupt". The design separates the two questions cleanly: **decryptability** comes from the envelope, **ownership** from comparing the stamp to the connection's own token, and trust never enters through the decryption path. Every one of the findings above is a finding about that second half — who gets told what — not about the first.

The other defences that survive scrutiny: the cleartext-plus-AAD shape is forced, and each alternative bricks a real scenario (defense 1); v1 stays readable and is upgraded on the next write (defense 3); the at-open fence warns rather than refuses, which is the only safe choice when an honest handover and a zombie's overwrite produce identical bytes (defense 4); the AAD freeze is byte-identical to the released bytes, because `VAULT_FORMAT_VERSION` was `1` at the merge-base and the literal reproduces the old string exactly — and the pin is not vacuous, since the test scans the builder's **body** for the constant rather than only asserting the value (defense 5, independently confirmed by the critic); the post-write re-read is the only observation point in the rename window (defense 6); the fence half of `snapshotIsCurrent()` catches the replaced-but-clean case the version counters cannot (defense 7); the `close()` cleanup order is right (defense 9); the two event codes and their Arabic badges are enforced from both sides by the source-scan tests (defense 10); the threat-model limit is stated honestly in the code rather than hidden (defense 11); and the `writeStamp` seam is fail-loud like `requireHeldLock` (defense 13).

Two defences are ruled against, on the code: **defense 8**'s "the failure mode of that choice is a redundant rewrite" is true for the pre-write check at `:355` and false for the post-write check at `:383`, where the same choice ends in `process.exit(1)` (finding 3); and its "one retry absorbs a transient EBUSY" is not supported by a retry with no delay between attempts (finding 5). **Defense 12**'s claim that every round-1 objection is closed checks out — I re-verified each one against the head.

The defender's accepted-limits list is the honest part of the change and mostly belongs in the PR body verbatim: detection is activity-gated and the heartbeat re-check is #287's lane; a deliberate writer holding the key and the folder is not held back; mixed fleets launder silently until every writer fences; upgrade is one-directional. One of them needs a correction before it goes in the PR body: the design scopes the laundering to "the v1 migration window" (`280-design.md:145`), but the same mechanism applies to a **foreign v2** — a zombie-written v2 envelope opens, decrypts, is served, and is re-sealed under the next holder's stamp, after which the evidence is gone. The laundering window is not a v1 property; it is a property of any foreign envelope.

## Recommended parent actions

1. **Fix in this PR (code).** Emit `VAULT_SNAPSHOT_FENCE_FOREIGN` at `:383` and `:430`; carry the fence outcome into the error instead of the hardcoded "another writer's envelope"; a failed read must not end in `process.exit(1)`; give the fence read the write path's 50 ms backoff; check the fence on the bytes `writeBackupTo` bundles; add the third code for the legacy case with its Arabic badge; say "read once at open" on `writeStamp`.
2. **Fix in this PR (prose).** The design record must not call a per-boot event "a load-bearing signal"; the cost line must say three reads on the dirty path; the laundering window must be stated as any foreign envelope, not only v1. The PR body carries the accepted limits verbatim — activity-gated detection, the per-boot meaning of `VAULT_SNAPSHOT_FENCE_FOREIGN`, the deliberate-writer boundary, one-directional upgrade, and the v1-in-a-backup-bundle exception that `docs/one-build-and-recovery.md` now documents.
3. **Open an issue** for the structural part of finding 1: a holder epoch (or a sidecar naming the previous token) so the at-open event can distinguish a zombie from an ordinary restart. Without it, the fence's signal is noise on every boot.
4. **Add to #287's brief:** the heartbeat piggy-backs a snapshot-fence verification, and the lock token must not rotate while a connection is open.
5. **Owner decision:** whether a fence refusal should take `main.ts`'s graceful in-use-refusal branch (like `VaultLockLostError` at `:267`) or stay fail-stop. Either is defensible; the current one reports the wrong cause.
