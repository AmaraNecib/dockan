## Critic findings — verdict-affecting

### C1 · severity 7 · an uncommitted or staged test file is only warned about, and the gate exits 0

`scripts/red-on-parent.ts:951-959` collects working-tree test files HEAD does not hold. `scripts/red-on-parent.ts:1234-1238` prints them as a `WARNING`. `scripts/red-on-parent.ts:1308-1309` decides `failed` from verdicts and problems only, and `scripts/red-on-parent.ts:1423` (the exit code) agrees. `uncommitted` is in neither.

Two outputs, both exit 0:

1. Author writes `packages/core/src/late.test.ts` and has not committed it. `files` is empty, so `renderReport` prints the warning and then `no added test files: nothing to gate` (`:1239-1240`). The file that should be judged is named once, above the line that says there is nothing to gate.
2. Author commits one gated file and leaves a second one staged. `files` has one entry, the verdict table is printed, and the last line is `red-on-parent: PASS`.

`--base HEAD` does not catch it either: `scripts/red-on-parent.ts:1024-1026` deliberately excludes the `headSha === baseSha && uncommitted.length > 0` case from `baseContainsHead`, so the "this run would pass having judged nothing" problem is suppressed for exactly this input.

The behaviour is pinned: `scripts/red-on-parent.test.ts:367-385` asserts `status === 0`.

### C2 · severity 6 · one waiver naming one test excuses every test in a file that never loaded

`scripts/red-on-parent.ts:470-476` builds `covers` as `.some(changeNames)`, takes `covering[0]` as the file's waiver, and emits a single `(whole file)` verdict. So a waiver that matches **any one** name the change registers clears the whole file.

Input (`packages/core/src/mixed.test.ts`, added by the change; `brandNew` exists only on the change):

```ts
import { expect, test } from "bun:test";
import { brandNew } from "./helper";
test("pins the new behaviour", () => { expect(brandNew(1)).toBe(1); });
test("already worked", () => { expect(1).toBe(1); });
// red-on-parent-waive: "pins the new behaviour" — rename: the test moved with the file
```

Parent run writes no junit (module resolves only on the change) → `WRONG_REASON_RED`, waiver attached, `verdictPasses` returns true (`:331-334`), exit 0. The second test is never judged and nothing in the report says so: one row, `(whole file)`, one waiver line. `scripts/red-on-parent.test.ts:956-968` pins the pass with a single-name `changeNames`, so the multi-test shape is untested.

This also contradicts the design doc it ships with. `.scratch/implementation/red-on-parent-design.md:150-152`: "The waiver names the exact test-name pattern it excuses … not a broad file-level skip." The built whole-file coverage is that broad file-level skip, one level up.

### C3 · severity 5 · the files the gate decides not to gate are never named, and the message claims there were none

`scripts/red-on-parent.ts:610-616` gates only `apps/**` and `packages/**`, excludes any path containing `/e2e/`, and excludes `*.spec.*`. Nothing records what was filtered out, and `scripts/red-on-parent.ts:1239-1240` reports the result as `no added test files: nothing to gate` whether the diff added zero test files or five that fell outside scope.

Input: this PR. `scripts/red-on-parent.test.ts` is added (1284 lines) and `scripts/red-on-parent.test.ts:867` asserts `isGatedTestPath("scripts/red-on-parent.test.ts") === false`. Running the gate on its own PR prints `no added test files: nothing to gate` and exits 0. `git ls-files | rg '\.test\.'` shows three more pre-existing test files in `scripts/` in the same position, so a new one is never gated and never mentioned.

### C4 · severity 4 · the copy manifest is written only after the whole loop, so an interrupted run orphans files in the cached worktree

`scripts/red-on-parent.ts:1096-1149`: each file is written into the base worktree and pushed to `copied`, and `manifestPath` is written once, after the loop. A throw inside the loop — `readAtRevision` (`:1098`) raises `GateError` when `git show head:<path>` fails, and an interrupt does the same — skips line 1148, and the `finally` only removes `outDir`. `clearPreviousCopies` (`:718-733`) then has nothing to delete on the next run, which reuses the same worktree (`:834-839`).

Consequence is noise, not a false pass: an orphan stays in the worktree, and the next run's parent side runs `bun test <relative path>` where the positional argument is a substring filter over discovered files (documented at `:239-242`). An orphan `apps/web/src/cart.test.tsx` is discovered by a later run of `apps/web/src/cart.test.ts`; if it throws at load the run prints `# Unhandled error between tests`, writes no junit, and the gated file reads `WRONG_REASON_RED` with a transcript from a file that is not part of the change.

### C5 · severity 4 · a path read from a file in the shared temp directory reaches `rmSync` without being checked against the worktree

`scripts/red-on-parent.ts:718-725` parses the manifest and returns it with a cast; `scripts/red-on-parent.ts:729-731` does `rmSync(join(worktree, relative), { force: true })`. `join` normalises `..`, so a manifest holding `"../../../apps/api/src/index.ts"` deletes that file, outside the worktree. The `SAFETY` note at `:720-722` states the worst case is "under-clear copies", which does not hold for a `..` segment. A non-string element throws `TypeError` from `join` — not a `GateError`, so `main` rethrows it as a stack trace (`:1425-1431`).

Reachability: the manifest lives under `cacheRoot` (`:704-711`), which is `tmpdir()` unless `RED_ON_PARENT_CACHE` is set. That is a directory the gate does not own exclusively, and the fix is one `resolve(...).startsWith(worktree)` check.

## Critic findings — report and documentation accuracy

### C6 · severity 2 · the header cites a bun pin the repo no longer uses

`scripts/red-on-parent.ts:16-17`: "measured on bun 1.4.2 (a dev machine) and bun 1.3.14 (the `packageManager` pin, which CI installs)". At this head `package.json:4` is `"packageManager": "bun@1.4.3"` and `.github/workflows/ci.yml:70` says setup-bun reads it from `package.json`. Same stale claim at `scripts/red-on-parent.test.ts:15` and `:694-696`.

The behaviour itself is covered: `scripts/red-on-parent.test.ts:669-707` runs a real `beforeEach` throw through the gate and asserts `WRONG_REASON_RED`, so a 1.4.3 change in the junit shape would turn CI red rather than silently pass. This is a stale sentence, not a live defect. The `assertions === null → treated as an assertion red` branch at `scripts/red-on-parent.ts:421-423` is the part the sentence is defending.

### C7 · severity 2 · the guard checklist states the opposite of the code for one verdict class

`.agents/skills/guard/SKILL.md:52-53`: "A wrong-reason red (the file cannot load on the parent) fails the gate". `scripts/red-on-parent.ts:331-334` lets a waived `WRONG_REASON_RED` pass, and `scripts/red-on-parent.ts:1186` tells the author to waive it for the rename case. A reader who trusts the checklist reads the pass as a misfiled waiver.

### C8 · severity 2 · a truncated invocation silently changes the parent

`scripts/red-on-parent.ts:1388-1395`: `--base` with no following argument sets `base` to `null`, which `resolveBase` (`:914-927`) reads as "use `origin/develop` or `develop`"; `--head` with no following argument sets `head` to `"HEAD"`. A dropped value gates against a different parent with no error.

### C9 · severity 3 · `RIGHT_REASON_RED` claims the test passes on the change, and nothing checks it

`scripts/red-on-parent.ts:1174` titles the verdict "the test fails on the parent for its own reason, **and passes on the change**". `changeSideResults` (`:979-1002`) is called only to enumerate names (`:1130-1136`), and its pass/fail status is discarded. Input: an added test that asserts a value the change does not produce — red on the parent, red on the change, `RIGHT_REASON_RED`, exit 0.

Defensible on scope: `bun run test` in `guard` and CI covers the change side. The defect is the sentence, not the gate. The report's contract should say "fails on the parent" and nothing about the change side.
