## 1. Critic findings

**C1 — SEVERITY 5 (Major) — a foreign-fence report can be lost permanently.**
`apps/api/src/db/encrypted-connection.ts:343-350` (`noteDiskStamp`).
`observedStamp` is committed **before** the logger call. Trigger: the logger's `warn()` throws on the tick that first observes the foreign stamp — `AppLogger.write` does `fs.appendFileSync` (`apps/api/src/lib/logger.ts:123`), so EACCES / ENOSPC / EBUSY on the log file does it. The heartbeat catches the exception (`lock.ts:289`), but `observedStamp` already holds the foreign stamp, so every later tick computes `changed === false` and `VAULT_SNAPSHOT_FENCE_FOREIGN` is **never emitted for that theft**. The version is still marked not durable and repaired, so the data outcome is right — the *naming*, which is the entire point of #292, is gone. Fix: report first, commit the observation after the log call returns (or mark it "unreported" so the next tick retries).

**C2 — SEVERITY 4 — the new heartbeat error log can escape the isolation boundary.**
`apps/api/src/lib/vault/lock.ts:280-281` and `:288-300`.
`this.runHeartbeatChecks()` sits **after** the heartbeat's `try/catch` (whose `catch` ends in `this.lost(...); return;` at `:277-279`). Inside `runHeartbeatChecks`, `check()` is protected, but the catch's own `this.options.logger?.error(...)` is not. Trigger: a check throws **and** the logger's `error()` throws (the same log-file fault as C1) → the exception escapes the `setInterval` callback. There is no `process.on("uncaughtException")` anywhere in `apps/api/src` → the process dies on an uncaught exception: no `VAULT_LOCK_LOST` line, no Arabic refusal page, an unclean exit with the SQLite handle open. That contradicts the code's own promise (`lock.ts:216-218`: "a failed diagnostic must never fail-stop a healthy instance").

**C3 — SEVERITY 3 — the test does not establish its claimed one-heartbeat bound.**
`apps/api/src/lib/vault/fence-heartbeat.test.ts:104-105`. `waitFor(..., 2_000)` against a 20 ms tick tolerates **100 ticks**. The design doc admits it ("a hundred ticks of slack over a bound the issue states as one"). A change that ran the check every 100th tick would still pass. Test quality is the test-audit's lane; this is a pointer, not a verdict.

## 2. Defender (arguing for the implementation)

- **Riding the existing heartbeat, no second timer** — `lock.ts:192, 220-222, 244-250`; `main.ts:262`. The lock already owns a 10 s `setInterval` with `unref()`; a second timer needs its own lifecycle and drifts from the lock cadence. **9/10.**
- **Checks run only after the identity check and the heartbeat write** — `lock.ts:258-265 → 280-281`. A lost lock returns before the checks, so a check never runs against a folder we no longer hold; the reported foreign fence can then only be a zombie, never a legitimate handover. **9/10.**
- **A throwing check is logged and skipped, not a lost lock** — `lock.ts:288-300`. Ownership is decided by `readOwnerOnce` + token compare and by `assertHeld()`, neither touched by this diff; routing a diagnostic failure into `lost()` would `process.exit(1)` a healthy instance. Pinned by test 4. **9/10.**
- **`recheckFence()` is strictly read-only** — `encrypted-connection.ts:456-473`. No write, no version bump, typed `(): void`; a heartbeat-triggered rewrite would serialize+encrypt a multi-MB image on a timer. It sets `fenceSatisfied = false` so the *next ordinary write* repairs, reusing the existing repair path. **9/10.**
- **Change-detection dedup, one change = one line, reset on repair** — `encrypted-connection.ts:343-350`. Without it the heartbeat would name the same theft every 10 s (86 400 lines/day); the reset at `:345` lets the next theft be named again; the key is the stamp *value*, so "same zombie" and "different zombie" are distinguished. **9/10.**
- **Reading the fence BEFORE a write** — `encrypted-connection.ts:475-478` and `:542-551`. `snapshotIsCurrent()` short-circuits on `mutationVersion === persistedVersion` (`:434`), so the post-write read only ever sees the stamp this process just wrote. Reading first makes the report independent of whether the version happened to be dirty — the common case would otherwise repair the zombie's envelope silently. **9/10.**
- **`diskFenceIsMine()` keeps its exact old semantics** — `encrypted-connection.ts:403-425` vs. the old inline loop. `readDiskFenceWithRetry()` (`:386-395`) is a faithful extraction: retry only on `"unreadable"`, return the first decidable answer, `"unreadable"` after the attempts. The decision table is identical in all four outcomes (`fence` → stamp compare; `absent`/`undecidable` → false; `unreadable` → warn + false). The only addition is the logging side effect. **10/10.**
- **No new event code, no contracts change, no envelope change** — `encrypted-connection.ts:349` reuses `VAULT_SNAPSHOT_FENCE_FOREIGN`; `sealSnapshot` / `readSnapshotFence` are untouched, so a vault written by this PR is readable by the previous build. **10/10.**
- **The detection only names the theft, it does not refuse to serve** — `encrypted-connection.ts:456-473`. Refusal would turn a *diagnosable, repairable* state into an outage for a shop that may have acknowledged transactions in memory. Refusal is reserved for the lock case (`main.ts:247`). **9/10.**

**Defender's rebuttals of the four objections I put to it** (these are the disagreements the synthesis turns on):

- **(a) the "unreadable" verdict logs every tick with no dedup** — factually right (`encrypted-connection.ts:466-471`), but the condition is a genuine I/O failure on a 76-byte prefix, not a steady state; the line is the only way the operator learns why the holder keeps rewriting (`fenceSatisfied = false` → repeated multi-MB rewrites); and deduping it would need a second piece of state that could hide a later FOREIGN behind the first verdict. **6/10** — the PR chose the right trade, at the cost of noise.
- **(b) "absent"/"undecidable" set `fenceSatisfied = false` with no log** — factually right (`:471-472`), but neither is a verdict about another *writer*: "absent" is a deletion (a legitimate restore or first run also produces it, and naming it a theft would be a false positive); "undecidable" is a *format* problem, and #280 gave the format its own code. Residual hole the defender names: a zombie writing **garbage** rather than a valid envelope lands in the silent branch. **7/10.**
- **(c) a check bound to a closed connection is never deregistered** — factually right (`lock.ts:220-222`; `release()` at `:314-330` clears the interval but not the array), but the lifetime problem does not arise in the wiring that exists (`main.ts:262` registers once; the lock is released on shutdown and `heartbeat()` returns immediately at `:253`), `recheckFence()` on a closed connection is a pure file read that touches neither the zeroed key nor the closed handle, and a `remove` API would be speculative generality for zero present callers. **8/10.**
- **(d) the detection does not prevent the loss if the holder crashes before the next write** — factually right and not claimed otherwise ("detected, not impossible"). No read-only detector can un-overwrite bytes a zombie already renamed over the file; prevention belongs to the lock/`writeGuard` path, untouched here. In the non-crash case the loss is fully repaired (the next write rewrites with the holder's own in-memory image). In the crash case the state is no worse than pre-PR; the PR's value is that the holder discovers it **while still alive**, inside one heartbeat, with the tenure named. **8/10.**

**Dismissed as false alarms** (checked, came back clean — recorded so the parent does not re-litigate them):

- *The detection bound does not hold.* It does: the lock's cadence is `heartbeatIntervalMs ?? 10_000` (`lock.ts:246`), `main.ts:67` does not override it, the check is registered once at unlock (`main.ts:262`), and the checks run only while the lock is ours. Bound = one heartbeat, plus event-loop scheduling.
- *The report can be lost in the normal path.* It cannot: `observedStamp` only ever takes a foreign value on a change, and a change is exactly the case that reports. Open / write / heartbeat each report a given theft exactly once; the repair (our stamp back) resets the key so the next theft is named again.
- *The report can be reported twice.* It cannot: whichever site sees the change first reports, the others see `changed === false`. The existing assertion `expect(foreignEvents).toEqual(["VAULT_SNAPSHOT_FENCE_FOREIGN"])` (`encrypted-connection.test.ts:451`) still holds under the new dedup — at open `observedStamp` is set to the foreign stamp, so the later write-path read is silent.
- *A healthy holder is failed-stopped by the detection.* It is not: `recheckFence` only sets `fenceSatisfied`, which makes the next write rewrite; the post-write fence read still decides durability and the retry loop is untouched. The only new fail-stop path is C2, which is a logger fault, not the detection.
- *The write path's fence read changed behaviour.* It did not: `readDiskFenceWithRetry` is a faithful extraction and `diskFenceIsMine`'s decision table is identical in all four outcomes. The open-time warn is preserved condition-for-condition and message-for-message.
