# Ticket #8 — invoice instalments: lessons from a High-assurance money review

**Date:** 2026-08-25 · Area: apps/api/src/{rpc/router,store}, apps/web/src/pages/invoice*

## A "no check-then-act race" claim only holds for ONE process (💡 Design Principle)

The in-process serialization queue makes an overpay guard read-then-write safe
for a single store instance, but the repo's own `allocateInvoiceNumber` and the
cross-connection store tests show multi-process atomicity is a real concern. For
money boundaries, make the DATABASE the authority: one conditional
`UPDATE ... WHERE remaining_amount >= ?` returning the affected-row count, inside
the same transaction as the insert + audit, refusing (rollback) on 0 rows. JS
recomputes (`paid + amount`) are then advisory fast-paths, not the guard.

## Both create paths must uphold the same money invariant (🔴 Major)

SALE creation recorded `initialPaid` as a payment row; PURCHASE creation did NOT
(`payments: []`), so a purchase's history disagreed with its header. When a money
trail exists for one invoice kind, check the other kind's create path for the same
row — the mismatch showed up only because the test asserted the history for a
purchase with `initialPaid`.

## Same-second timestamps + UUID ids = shuffled history (🔴 Major)

`payments` history ordered by `(paid_at, id)` is a coin-flip when two instalments
land in the same second, because `id` is a `randomUUID()`. Tie-break on `rowid`
(insertion order), the pattern `listStockMovements`/`listActivities` already use.
The flake appears under load as an ORDERING failure in a test that asserts
sequence — write the fixture with a REUSED timestamp to pin it deterministically.

## Order-guided review beats green tests (🟡 Minor)

The fastest path to a correct money feature is an adversarial wave: the critic
found the cross-process race and the initial-payment-row gap that a green suite
cannot see. The web-mock trap (`mutationOptions` dropping onSuccess/onError) and
the prefix- vs exact- query-key invalidation difference were both caught by
component/E2E tests, never by typecheck.

## TanStack v5 invalidation: exact keys proven, prefix keys ambiguous (🟡 Minor)

In this repo's loaded TanStack build, invalidating a mounted detail query by its
EXACT generated key refetches reliably (E2E-verified); prefix-only keys did not
trigger the refetch and flaked the E2E. Treat a load-bearing refetch as exact-key;
prefix keys are best-effort only (the list still refreshes on remount).

## Tooling: bash heredocs truncate large content here (🟡 Minor)

Big `cat << EOF` blocks get cut mid-stream. For large appends, write the content
to a temp file with the write tool, then `cat file >> target`; for multi-file
evidence assembly, write a python builder script file and run it.
