## Axis B — standards & code quality

`AGENTS.md` is only a search-scope note (8 lines); it is respected in this review (all greps scoped to the worktree). `docs/engineering-workflow.md` was **not read** this round, so I cannot attest workflow-conformance; what follows is the code-quality axis from the diff itself plus the guard artifact.

Fowler-style observations, all grounded in the diff:

- **Long Function / divergent responsibilities — `suppliersReturn` (router.ts, the block containing the guards at :838/:844/:847, ~110 lines).** One closure does invoice/line validation, cap checking, line snapshotting, `returnNumber` allocation, return + line inserts, a per-line stock projection + weighted-average cost recompute + `setItemStockAndCost`, three signed-entry branches, and activity. The stock/cost block reuses the sale-side ledger helpers correctly, but the handler is well past the point where extracting a `recordPurchaseReturn(tx, input)` use-case (or at least `applyReturnStock(tx, line)`) would pay off. Same shape, smaller, in `suppliersPay` (`payInvoice` nested helper at router.ts:691–712 is a good local extraction — this pattern is the model to follow).
- **Duplicated Code — payment-entry construction.** `insertSupplierEntry({kind: "PAYMENT", ...})` is written at router.ts:702, :732, ~:1126 and ~:1195 with subtly different field sets: the two invoice-create paths omit `note`, `paymentsCreate` includes a trimmed `note`, and one path omits `ref`. Behaviourally fine today; a single `recordSupplierPaymentEntry(tx, {...})` helper would remove the drift surface on a money table.
- **Inconsistent value computation — return preview vs validation.** `invoiceValue` in `supplier-return-panel.tsx:59–66` recomputes from the raw drafts with `Number(...)`, while submission uses `parseReturnQuantities`. An invalid fractional draft therefore still produces a nonzero preview total (the error banner + disabled button contain the risk). Deriving the preview from `parsedQuantities` would make preview and submission provably one computation.
- **Repeated read-modify-report.** `listSupplierEntries` → `supplierBalance` → insert appears three times (router.ts:736–737, 853–854, 866–874). A `supplierAccountState(tx, supplierId)` helper is a cheap consolidation.
- **Sentinel-shaped return** `number | null` from `supplierChargeEntryAmount` is acceptable (tested, documented) — noted only for consistency with the codebase's other `| null` parsers.
- **UUID fallback rendered to the owner** (`record.supplierName ?? record.supplierId`, returns.tsx:222 and supplier-return-print.tsx:69). The FK makes the fallback unreachable; harmless, but it would show a raw UUID if it ever fired.
- **Test quality is genuinely behavioural** (wire-level for the zero purchase, DOM-level for the panels, store-level for the join) — this is the right level for a high-assurance money change.
