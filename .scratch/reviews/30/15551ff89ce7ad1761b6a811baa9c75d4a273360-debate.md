## Greptile findings (both fixed with regressions)

- **Stale pricing snapshot (P1):** item resolution moved inside `withTransaction`
  via `tx` — pricing, FIFO, and persistence share one committed snapshot; all 56
  router tests pin identical ITEM_NOT_FOUND / PAID_EXCEEDS_TOTAL semantics.
- **Interrupted migration (P1):** backfill gated by a durable settings marker
  (`migration.saleColumnsV1`) inside one SQLite transaction instead of column
  presence, so an interrupted upgrade re-runs on next boot until complete.

## Follow-up review finding (4/5 confidence — confirmed valid, fixed)

> **Backfill corrupts default-price snapshots:** markerless databases upgraded
> from the pre-marker implementation contain legitimate modern sale lines with a
> zero default price and positive negotiated price; the backfill's
> `default 0 AND unit > 0` predicate rewrote those as legacy, corrupting
> `defaultUnitPrice` permanently.

Confirmed: pre-marker-era databases (this PR's original implementation) never
wrote a marker and can hold such rows, so the marker-gated backfill re-ran over
live data. Fixed by healing only rows carrying the full **pre-migration
invariant** (`default 0 AND unit > 0 AND discount_allocated = 0 AND
net_total = 0`): modern zero-default lines can never match (undiscounted ⇒
net = gross > 0; discounted ⇒ allocated > 0). The invoices UPDATE mirrors the
read-time normalize heuristic (adds `discount_type IS NULL`). Interrupted-legacy
rows still heal; completed or mixed markerless DBs re-run as no-ops; marker
still written once. Regression proved in drizzle-store.test.ts (markerless DB
with modern undiscounted + fully-discounted zero-default lines and one legacy
line: modern preserved, legacy healed, marker set, second setup no-op).
