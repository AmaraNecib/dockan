# Debate — issue 191, head `643e165b82f8c1b2781f298599b979bf00cf95a4`

Base `da44b502d39c79a1368e9848542d9a25fac301fc`. Critic and defender ran as
separate read-only reviewers on the same commit; this file is the parent's
synthesis, and the change was revised where the critic landed.

## Critic (findings)

1. **BLOCKER — the disabled-click mechanism is unreachable and unproven.** The
   change's commit body claimed "a click the browser swallows on a disabled button
   sends no request at all — the 30 s timeout this issue reports". That needs
   `createWithStock.isPending === true` (sale.tsx:608) while the button is in the
   DOM, but the button renders only with a cart line (sale.tsx:595) and the line is
   added in the mutation's `onSuccess` (sale.tsx:445). The pre-fix spec's
   `sale-total` assert already proves the line existed, so the button was enabled
   when the ack was armed. Zero of the author's own 120 instrumented runs showed
   `saveDisabled:true`. **Accepted.**
2. **MAJOR — the budget explanation is ignored and the change tightens it.** A
   `page.waitForResponse` timeout is emitted by whichever wait is outstanding when
   the 30s budget dies; it does not prove a request was never sent. **Accepted as
   the honest reading; the commit body now says exactly this and no mechanism is
   claimed.**
3. **MAJOR — the new acks convert a ≤5s refusal failure into a 30s hang.** If
   `quickSubmit`/`submit` refuse client-side (sale.tsx:322-407, 419-441) they send
   no request, so the armed ack can never resolve. **Accepted and fixed** — each
   action now asserts `sale-error` is empty immediately after its click, so a
   refusal fails by name inside the 5s expect window.
4. **MAJOR — the evidence is unreproducible and cited paths did not exist.**
   `.scratch/reviews/191/` did not exist at review time. **Accepted and fixed** —
   this file and its siblings exist, and the measurements are recorded in
   `-verification.md`.
5. **MINOR — `sale-error` count 0 is a diagnostic, not a gate.** Correct: `submit()`
   never branches on a pre-existing error. The comment no longer calls it a gate;
   the pre-click check was replaced by the in-action asserts above. **Accepted.**
6. **MINOR — the ack payload was discarded** while the design justified itself with
   it. **Accepted and fixed** — the created `id` is bound and asserted against the
   cart row (`name="quantity-<id>"`), so the spec now proves the row the save sends
   is the one the api issued.
7. **MINOR — no reuse/regression guard for the seven sibling specs; no tracked
   follow-up.** **Accepted as a follow-up**, handed to the parent in the lane report
   (not silently dropped); extracting an `ackQuickAdd` helper across eight specs is
   out of scope for this issue.
8. **MINOR — line-cite drift (596 vs 595).** **Accepted and fixed.**
9. **DISMISSED — procedure name, testids and assertion shapes.** The critic agreed
   `itemsCreateWithStock` is correct, `sale-lines`/`sale-save`/`sale-error` exist and
   are unambiguous, and `actAndAck`/`rpcOutput` are used as intended.

Debate detail worth recording: the critic asserted the ordering as "`onSuccess`
runs *after* React Query clears `isPending`". The installed source is the opposite —
`await this.options.onSuccess?.(…)` then `dispatch({ type: "success", data })`
(`@tanstack/query-core@5.101.4` `mutation.js:160`) — but both updates land in one
React commit in practice, so the critic's *conclusion* (no reachable disabled window
in the observable DOM) matches the 0/120 measurement either way. Neither ordering
claim is used to justify the change.

## Defender (verified claims kept)

- The form really posts `itemsCreateWithStock` for the spec's input: `openQuick()`
  runs with `withStock=false`, the spec fills stock `2`, `resolveOpeningStock("2",
  false)` → `{ok:true,value:2}` (numeric-input.ts:38) so `stock.value > 0` takes
  `createWithStock.mutate` (sale.tsx:445), bound to `orpc.itemsCreateWithStock`
  (sale.tsx:208, contract app-contract.ts:111). Arming `itemsCreate` (as the crew
  brief suggested) would never fire.
- The cart line comes only from the response: `addLine` is called from `onSuccess`
  and from the picker/scan paths; the row is keyed on `line.item.id` (sale.tsx:584).
- `sale-save` is genuinely disabled by the item write (sale.tsx:608), and the
  pre-click `toBeEnabled` assert is what turns that into a named failure.
- The new gate asserts cannot fail on a healthy run: measured pre-click state is
  always 1 row, value 1, enabled, no error.

## Verdict

One blocker raised, all its substance accepted and the change revised. The two
cheap improvements the critic recommended (keep the asserts, make a recurrence
attributable) are in; the recommendation to "reopen #191 rather than close it" is
carried into the lane report as an explicit uncertainty for the parent, since the
surviving evidence cannot pin the CI stall to a single mechanism.
