# One unlocked vault, one session, and the cookie holds the credential

Two windows of the same browser must both work against one unlocked vault, because the v1 scope statement promises it — a sale in one window moves the numbers in the other. The audit found the opposite. The API held exactly one live session token, the unlock path replaced it, and the web kept it in per-window `sessionStorage`, so a second window's unlock silently killed the first window's calls: no message, no gate, just queries that stopped resolving. The choice was **share or refuse**, and it had to be written down before any code changed. We **share**, and the credential moves into an HttpOnly cookie.

The cookie is what makes sharing free rather than a new server surface: a browser's cookie jar is shared by every window of that browser, so the token stops being per-window data and both windows present the same credential. The same move tightens the exposure — `HttpOnly` means the page can no longer read the token, which is strictly less than the `sessionStorage` it replaces, because an XSS in the web app can no longer exfiltrate it. The owner session already worked that way: the dev server proxies `/api` so the better-auth cookie stays same-origin.

The API keeps exactly one live token, as it did before. It was not widened into a set of simultaneously valid tokens: a stolen token must still die at the next unlock and on lock, and a set would outlive it.

**Considered options**

- **(A) Refuse a second window out loud.** Rejected: it leaves the v1 scope promise unmet, and it answers a problem the cookie removes for free. The refusal path still earns its place for the case that genuinely is one — a session that was replaced, locked or logged out — which the gate now states in words instead of leaving to failed queries.
- **(B) Share the session with a token set on the API.** Rejected: it is the only way to keep several tokens alive at once, and it widens what a stolen token can do. The issue puts that out of scope, and a long-lived old token is the same class of surprise that produced this defect.
- **(C) Share one session through the token the API already had, carried in an HttpOnly cookie.** Chosen.

**Where the implementation pins it**

- The transport decision lives in one module, `apps/api/src/lib/vault/session.ts`, and both seams ask it: the vault routes and the RPC guard. The **server's mode** decides which transports are readable, and the request decides which of them it uses. A browser-mode server reads the cookie first and the `x-vault-session` header when the request carried no cookie at all, for clients that hold a token (curl, the e2e helpers, the dev tooling); a broker-mode server reads the header only, so a page that happens to hold a cookie of the same name on the same host cannot present itself as the native transport.
- The cookie is `HttpOnly; SameSite=Strict; Path=/`, host-only (no `Domain`), and `Secure` where the origin qualifies — HTTPS, or a loopback host, which is a secure context and where Chrome and Firefox both accept `Secure` over plain HTTP. Logout clears it with `Max-Age=0` and the same attributes. A request is read for **every** cookie of that name, not the first: browsers send duplicate names longest-path-first (RFC 6265 §5.4), so a cookie planted on a longer path arrives ahead of the live one on `Path=/`, and a server that took the first match refused a request whose live credential was in the same jar. Each candidate is tested against the one live token, so a planted value costs a comparison and never access.
- A browser-mode server refuses a request whose `Origin` is not this app's **own** origin — the host and port the request was addressed on — on any loopback-required route and at both seams. The scope is the loopback-required set, not every vault route: `/api/vault/status` reads the credential (it has to, to answer `session`) and is deliberately reachable, so a status read names no refusal and leaks only the two booleans below. The rule is one function in `session.ts` that both seams call, and it is deliberately not the weaker "is this a loopback origin": cookies ignore ports and `SameSite` is scoped by site, so a page on any other loopback port is same-site with the API, arrives with the live cookie attached, and passed the loopback test. Only the origin the app is actually served from matches now, so a different port on the same host is refused. An **absent** `Origin` is accepted: `SameSite=Strict` is what stops a cross-site request from carrying the cookie at all, and the non-browser clients that legitimately present a token (curl, the e2e helpers) send none. The origin rule is scoped to browser mode because the desktop webview's own scheme is not an http origin and the shell is the trusted party there.
- On the browser path the unlock, setup, recovery-unlock, change-passphrase, reset and recovery-key replies carry `sessionGeneration` (where they carried one before) and **no token**; the token exists only in the `Set-Cookie` header. The broker path is unchanged and still returns the token in the body.
- A **minting** reply installs a credential only if the session it minted is still the live one. The browser applies a `Set-Cookie` whatever the page decided, so a reply slow enough to be overtaken by another window's unlock would otherwise overwrite the live cookie with a token the winner already revoked, signing every window out. A reply whose session was superseded therefore carries no credential at all — no cookie, no token in the body — and reports the generation in force. The mutation it answered already happened; only the credential is dropped. The generation is what "still live" means, so it advances wherever the token is dropped — a rotation, a logout, and a lock — not only on a mint: a revoke that cleared the token without moving the number left a late reply matching an epoch that described a session the server no longer held.
- **That arbitration is a check at build time, not a law about delivery.** The reply is judged when it is built; the browser applies its headers whenever they arrive. So what the rule closes is the **mint → build** window: a reply whose session was already superseded when its body was assembled carries no credential at all, so it cannot install one. What it cannot close is **delivery order**: a reply built while its session was live and delivered after a later unlock still carries `Set-Cookie` with the dead token and overwrites the jar's live one, and the browser path has no way to reject it — `storeVaultSessionToken` is only reached when the body carries a token, which browser mode omits, so the page never sees the header it would have to refuse. The status probe does not recover it either: it reads the overwritten dead cookie, so `session` is false and the owner lands on the unlock screen. The same is true of the one reply the rule was already known not to govern: a **clearing** one, where a logout overtaken by another window's unlock still carries `Max-Age=0` and clears whatever cookie is in the jar at that moment. Both cost a passphrase and nothing worse: no path here turns a delivery-order overwrite into access. Stated here so a later reader does not read the guarantee as wider than it is.
- The web holds no token in `sessionStorage` on the **browser** path — nothing under `dokan.vault.session` or `dokan.vault.session-generation`. That is the path where the cookie is the credential and the page must not be able to read one. The **broker** path keeps its token and generation in `sessionStorage`, as it did before this change, because there the page already holds the token in memory to sign its RPC calls: storage adds no exposure it did not have, and it is what lets a webview reload keep working (the broker refuses further commands once it has been served, so a reload that forgot the token could not be recovered even with the right passphrase). One thing the page does persist on both paths is a **boolean** under `dokan.auth.signed-out`: the owner asked to sign out and the server could not confirm the revoke, so the next page load must not read the live cookie and mount the app. It is not a credential — it carries no token, cannot be replayed to the server, and its only effect is to keep the unlock screen up, so a page that forged it would deny itself the app rather than gain it.
- A refusal (the session was replaced, locked, or logged out) arrives as `UNAUTHORIZED` / `AUTH_REQUIRED` — one pair exported from `@dokan/contracts`, because a hand copy on each side meant renaming one left every test green and the unlock screen never rose — and the app answers it by raising the unlock screen instead of leaving a page of failed queries: the store lives in `apps/web/src/lib/auth-refusal.ts` and the RPC interceptor marks it. A foreign-origin refusal is a different code, `VAULT_ORIGIN_FORBIDDEN`, and is not that answer.
- The status route answers whether **this request's** credential is the live session, so a window with no valid cookie lands on the unlock screen instead of mounting the app and being sent there by its first refused query. A boolean discloses nothing to a caller that already holds, or lacks, the credential it describes.

**Consequences**

- The vault session leaves `sessionStorage` on the browser path. On the broker path it stays where it was.
- The cookie is host-scoped and port-agnostic, so another process serving `http://127.0.0.1` can write a cookie of the same name. The API accepts only its own live token, so a written-over cookie produces a refused session — the unlock screen — never access to the vault. A cookie planted on a longer path is refused the same way: it is tested and rejected like any other candidate, and it cannot shadow the live one any more. The same applies to the cookie being overwritten by the second window's unlock: that is the intended behaviour, and it is why the client's stored generation is no longer a credential.
- **Riding the cookie is a different limit from overwriting it, and the origin rule is what closes the browser half.** A page on another loopback port is now refused, because its `Origin` is not this app's. What an origin rule cannot close is a local *server*: cookies ignore ports, so after the owner unlocks at `http://127.0.0.1:5173`, any other program listening on `http://127.0.0.1:<other port>` is sent that cookie, and it can replay it as its own `Cookie` or `x-vault-session` header from a process that sets any `Origin` it likes. Closing that needs the app to stop sharing `127.0.0.1` as a host with every other local server, which changes dev, e2e and desktop URLs; it is recorded as its own decision, not something this design pretends to have solved.
- **The header branch is the same limit, one step earlier, and it is not page-exploitable.** On a browser-mode server `resolveVaultCredential` returns a **header**-carried token before the origin check (the cookie branch is the one that asks), so at `/api/rpc` an `Origin` of the caller's choosing plus `x-vault-session` is accepted. That is the local-server replay above arriving through the other transport, and it needs the token first. A page cannot reach it either: a cross-origin request with a custom `x-vault-session` header is not a simple request, so the browser sends a preflight, and this server answers no preflight. It is written down rather than "fixed", because the fix is the same host decision (#343), not a second origin check that would refuse the curl and e2e clients this branch exists for.
- Nothing clears the cookie on **lock**: there is no lock route, and the server-side token dying is what ends the session. The cookie left behind names a token the API no longer accepts, so it reads as a refused session on the next call. **Logout** is the case that does clear it, with `Max-Age=0`, because there the owner asked to end the session and the cookie would otherwise outlive the revocation on a shared machine. Logout only reloads once the revoke was **confirmed**, or once the server said there was nothing to revoke — no live session, or a build with no vault route at all: in both of those the page's own clear was the whole credential. "No vault route" is **asked** of the status route, never inferred from one hop's 404: a proxy answering for a route it does not forward reads exactly like a build without it, and reading that as absence reloads the page with a live cookie attached, which lands back in the app. The one case that holds the page is an **unconfirmed** revoke: the page cannot disable an `HttpOnly` cookie, so a reload there would land back in the app, and the unlock screen rises in place instead, remembered across a reload so an F5 cannot undo it. **The residual is worth stating plainly:** when the revoke is unconfirmed the cookie DOES outlive the failed sign-out — the design keeps it and refuses to reload, which is the lesser of the two failures but not the promise the sentence above makes. On a shared machine, an unconfirmed sign-out leaves a live cookie in the jar; what puts the next person on the unlock screen (and `SameSite=Strict`, host-only scoping) is a speed bump, not a cleared cookie — the flag is one `removeItem` away from letting them through, and it is the unlock screen that actually asks for the passphrase. **And the hold is this window's, flag included:** the persisted half lives in `sessionStorage`, so a sibling window neither receives it nor is gated by it — and a sibling that reloads comes back into the app, because its own credential really is live. That is the honest consequence of holding per window rather than per origin: one window's failed sign-out cannot protect another window, and pretending otherwise (a shared `localStorage` flag) gated siblings that had never asked to sign out.
- A refusal is recoverable without a rotation. A transient one — a query in flight across another window's credential change — is answered by one status read: if the server reports this request's credential live again, the unlock screen comes down. Re-entering the passphrase was the only exit before, and it rotates the token, which refuses the window that was working.
- The desktop broker transport is unchanged: the secret crosses the native bridge by design there, and the broker is a separate channel from the browser's cookie jar.
- The e2e helpers still read the old storage key and fall back to no header. Nothing breaks — the seeded request already sends `credentials: "include"`, so the page's cookie authenticates it — but the read is dead weight now and belongs in a follow-up.
