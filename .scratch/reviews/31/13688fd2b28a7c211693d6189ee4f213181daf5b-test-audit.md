## Round 3 — greptile PR finding fixed (13688fd)

**Finding:** two processes running setup() concurrently on a fresh/partially-seeded
database both read under a deferred snapshot; the loser's read-to-write upgrade died
with SQLITE_BUSY_SNAPSHOT mid-startup.

**Fix (13688fd):** seedExpenseCategories opens with BEGIN IMMEDIATE so the write lock
precedes the marker/rows read; the concurrent loser waits on busy_timeout and re-runs
as a no-op against the winner's committed marker. Marker/self-heal logic untouched.
Extracted to an exported module function because setup() already holds the store's
serialization queue and cannot call StorePort.withTransactionImmediate without
deadlocking — same SQL primitive, inline.

**Regression (drizzle-store.test.ts):** deterministic lock-first unit test — a second
connection holds the write lock while the seed runs with busy_timeout=250ms; an
exec/query spy records that the fixed unit throws at its BEGIN IMMEDIATE having
issued no other statement (a deferred begin reads rows+marker first), then heals to
exactly the seven defaults once the lock is released. Verified discriminating: fails
against a deferred-begin revert, passes with the fix.

Gates at 13688fd: typecheck ✓ lint ✓ unit 285 api + 61 web ✓ e2e 16/16 ✓ port
restored byte-exact ✓.

**Noted, out of scope:** setup()'s earlier invoice_number_sequence conditional INSERT
also queues on the write lock under contention; it is a single autocommit statement
