# Test audit — PR #297, `red-on-parent` gate

**Head** `6c45f2f593dcfb346f7892b4112de8454ae395b3` · **base** `bff7a1a9d9d15b59470bd2452a61e180b90c4b6a`

Nothing was executed except a regex/`$`-anchor check and a count of the test cases. No suite, build or e2e was run; the parent owns that in the heavy queue.

## 🔴 Critical

### F1 — The gate never checks that the added test passes on the change, and the suite never asks either

**Where** `scripts/red-on-parent.ts:1174` (the guide text), `:979-1001` (`changeSideResults`), `:1130-1141` (the caller).

`VERDICT_GUIDE` tells the reviewer the test "fails on the parent for its own reason, **and passes on the change**". The gate runs the change side — `changeSideResults` parses its junit into full `TestResult[]` — and then uses only the *names*: line 1136 takes `changeResult.name` / `displayName(changeResult)`, and `unregisteredVerdicts` (`:537-577`) compares display names. The `status` of every change-side result is read nowhere. The data is collected and thrown away.

**Triggering input.** Base `helper.ts` throws `"zero"`. The change leaves `helper.ts` untouched and adds `packages/core/src/red.test.ts`:

```ts
test("rejects zero", () => { expect(() => guard(0)).toThrow("ZERO"); });
```

Parent side: assertion red → `RIGHT_REASON_RED` → exit 0 → report says "and passes on the change". The test is broken on the change too — `guard(0)` still throws `"zero"`, so it fails there as well. The gate certifies it.

**Why the suite misses it.** The mutation proves it: in the e2e fixture at `scripts/red-on-parent.test.ts:185-210`, replace `HELPER_AFTER` with `HELPER_BEFORE` so the change becomes a no-op. The gate still prints `RIGHT-REASON-RED` and still exits 0, and the assertions at `:206-207` still hold. No test in the file reads a change-side status.

**Fix.** Either check it — a test that is red on the change is not a right-reason red, it is a broken test, and deserves its own verdict — or stop promising it in `VERDICT_GUIDE`. Right now the report makes a claim the code cannot back.

### F2 — The timeout → `RUN_INCOMPLETE` wiring is untested, and a timeout can become a waivable pass

**Where** `scripts/red-on-parent.ts:1115-1118` (error string), `:640` (`spawnSync`'s `timeout`), `scripts/red-on-parent.test.ts:994-1002`.

The only timeout test hands `classifyFileRun` a hand-written string — `"hit the 120000ms timeout"` — that the code never emits. The producer is never run: no test asserts that `run()` passes `timeout: TEST_TIMEOUT_MS` to `spawnSync`, and no test asserts that `result.status === null` becomes that error string.

**Triggering input.** A parent-side test that hangs. `spawnSync` kills it, `status` is `null`, and the gate reports `RUN_INCOMPLETE` (no waiver covers it — the design's fail-closed rule, §4 step 6).

**Why it matters.** If `error` were always `""`, the same hung run becomes a junit-less `WRONG_REASON_RED`, which a whole-file waiver excises (`verdictPasses` → `true`) → **PASS on a hung run**. No test in the suite fails under that mutant. Dropping the `timeout` option from `spawnSync` (an infinite hang) is equally invisible.

**Fix.** `TEST_TIMEOUT_MS` is a hard-coded const, so no end-to-end fixture can exercise this without a 120-second test. Make it injectable (`RED_ON_PARENT_TEST_TIMEOUT_MS`) and add a fixture whose test hangs for 1 s, asserting `RUN_INCOMPLETE` and exit 1 with no waiver able to cover it.

## 🟠 Major

### F3 — A waiver that matches no test is never asserted to fail the gate

**Where** `scripts/red-on-parent.ts:588-599` (`unusedWaiverVerdicts`), call site `:1144`; `scripts/red-on-parent.test.ts` has **zero** occurrences of "matches no test".

The suite calls `unusedWaiverVerdicts` twice (`:1040`, `:1134`) and both times asserts an **empty** result. The failing branch — a waiver that matched nothing → `WAIVER_MISFILED` — is never asserted, and no end-to-end fixture carries a stray waiver.

**Triggering input.** An added file that loads on the parent with a red test, plus `// red-on-parent-waive: "no such test" — stale`. The waiver excuses nothing and must fail the gate.

**Mutation.** Delete the call at `:1144` → the whole suite stays green, and a typo'd waiver (`"rejects zro"`) never fails the gate again. Same hole for a waiver whose pattern names another file's test.

### F4 — The gate's per-file promise is never tested with two added files

**Where** every fixture in `scripts/red-on-parent.test.ts:184-560` adds exactly one test file.

**Triggering input.** A change adding `packages/core/src/a.test.ts` (red on the parent) and `packages/core/src/b.test.ts` (green on the parent, no waiver). The gate must fail on `b`.

**Mutation.** `files.slice(0, 1)` inside `runGate` → the suite stays green and the second file is never judged. The gate's whole selling point is "every added file is gated".

### F5 — The change-side failure paths (`problems[]`) are untested

**Where** `scripts/red-on-parent.ts:985-990` ("has uncommitted changes") and `:993-1000` ("the change's own run wrote no junit report"); neither string appears anywhere in the suite.

**Triggering input.** Commit the added test file, then edit it in the working tree. The gate must fail closed: it pushes a problem and exits 1.

**Mutation.** Drop either `problems.push` → the change-side list is empty, `unregisteredVerdicts` has nothing to compare, and the gate prints PASS on a file whose content differs from HEAD. The test at `:367` covers an *untracked* file, which exercises the other warning path, not this one.

### F6 — `parseArgs`, `lockWaitBudget`, `loadFailureReason`, `addedTestFiles`, `uncommittedTestFiles` have zero references in the suite

**Where** the import block `scripts/red-on-parent.test.ts:32-49` omits all five; grep counts are 0 for each.

**Concrete input.** `bun scripts/red-on-parent.ts --base` with no value → `red-on-parent.ts:1391` does `parsed.base = argv[index + 1] ?? null` → `resolveBase` (`:914-926`) falls back to `origin/develop`, so the gate silently tests a *different parent* instead of erroring. Untested: `--base=<rev>`, `--head=<rev>`, `--help`, an unknown argument (exit 2), and `resolveBase`'s default — the path CI would use, since every fixture passes an explicit `--base`.

**Mutants that pass the whole suite:** `--base=x` broken; the default base broken; `lockWaitBudget`'s arithmetic wrong; `loadFailureReason`'s "the file declares no tests" branch (`:580`) and its fallback (`:584`) wrong — so a parent file that declares no tests is still reported as "could not load".

### F7 — No end-to-end fixture for a skipped parent test, a duplicate display name, or two waivers on one test

**Where** `scripts/red-on-parent.test.ts:982`, `:1043`, `:1122`, `:1252` call `classifyFileRun` / `unregisteredVerdicts` directly.

A defect **at the call site** — `red-on-parent.ts:1133-1144`, where the two classifications are merged and the unused waivers are collected — is invisible to those tests: a wrong argument, a stale `used` set, or a dropped `unusedWaiverVerdicts` call all leave the unit tests green.

### F8 — The "trap" test proves a hand-written literal, not bun's behaviour

**Where** `scripts/red-on-parent.test.ts:715-748`. `hookTranscript` (`:721-725`) was written to satisfy the suite's own `naiveGrepVerdict` helper (`:155`), so `:735` is a tautology about the helper's own code. The real transcript is never captured: the gate prints only the error excerpt (`red-on-parent.ts:1295-1300`) and the end-to-end hook fixture (`:669-711`) asserts the verdict only. The suite header (`:9-19`) states that "the transcript *does* carry that line" is asserted — it is not.

**Triggering input.** Bun changes its reporter (drops the `(fail)` prefix). The test at `:735` stays green while the advertised contrast — "a grep-based gate would be fooled here" — silently stops holding. What is verified is that the gate reads the junit counter; what the suite *claims* it verifies is that bun prints `(fail)`.

**Fix.** Run the fixture's parent-side file directly in the fixture repo, capture the real transcript, assert it contains `(fail)`, and feed that capture to `naiveGrepVerdict`.

### F9 — The report's own PASS/FAIL line is never asserted, and the one assertion that touches it is vacuous

**Where** `scripts/red-on-parent.ts:1308-1309`; `scripts/red-on-parent.test.ts:1240`.

"red-on-parent: FAIL" appears **0** times in the suite; "red-on-parent: PASS" appears once, in `expect(report).not.toContain("red-on-parent: PASS")` — and `renderReport` returns early in the `files === 0` branch (`red-on-parent.ts:1239-1250`), printing neither PASS nor FAIL, so that assertion can never fail for any implementation of that branch.

**Mutation.** `const failed = false` in `renderReport` → no test fails. The exit code is computed independently in `main` (`:1423-1424`), so the gate's *decision* is safe; what is unprotected is the line a reviewer reads.

**Fix.** One line each: assert `toContain("red-on-parent: FAIL")` on the GREEN-ON-PARENT fixture (`:252`) and `toContain("red-on-parent: PASS")` on the RIGHT-REASON-RED fixture (`:185`).

### F10 — No test sets a timeout while 17 tests spawn a real gate run

**Where** `scripts/red-on-parent.test.ts:185, 212, 252, 280, 309, 338, 367, 387, 411, 451, 492, 553, 568, 600, 614, 630, 652`.

Each spawn does `git worktree add` plus up to two `bun test` processes. The repo has **no root `bunfig.toml`**, so bun's default 5 s per-test timeout applies, and no test passes a timeout argument — the only `timeout:` in the file (`:123`) is the inner `spawnSync`.

**Worst case `:652`** ("two runs on one base"): the second run waits on the lock, whose budget is `lockWaitBudget` = 600000 + 120000 + 60000 ms (`red-on-parent.ts:1005-1010`) — a 5-second test waiting on a 13-minute queue. `runGateAsync` (`:129-141`) sets no spawn timeout, so a hung child leaks.

**Fix.** `test(name, fn, 60_000)` on the 17 spawners, plus a timeout in `runGateAsync`.

### F11 — The uncommitted WARNING is false for a modified tracked test file

### F12 — The weakest end-to-end assertion

`scripts/red-on-parent.test.ts:185-210` (the RIGHT-REASON-RED fixture) asserts only `toContain("RIGHT-REASON-RED")` and `status === 0` — no test name, no file row, no verdict count. A mutant that classifies the *file* rather than the *test* passes it. Only the NOT-ON-PARENT fixture (`:411`) pins a test name.

### F13 — Fixture fragility

`commitAll` (`:76-89`) pins `user.email`/`user.name` but not `commit.gpgsign=false`; a machine with global signing fails every fixture with a raw git error rather than a skip. `cleanup` (`:102-104`) calls `rmSync(..., { force: true })` with Node's default `maxRetries: 0`, so one Windows EPERM (git still holding the worktree) throws out of the `finally` and masks the real assertion.

### F14 — The install path and `--fresh` are never exercised

No fixture repo has a `bun.lock` (`:172`), so `ensureBaseNodeModules` (`red-on-parent.ts:864-886`) returns `""` at `:868` and the marker logic (`:875-882`) never runs — that logic is precisely what prevents an added test importing a workspace package from loading the *change's* source and passing a gate that is testing the parent (`:855-861`). `"--fresh"` appears 0 times in the suite.

## 💡 Design Principle — the gate is not wired where the design says it runs

Design §4 ("Where it runs") puts the gate in **CI on the head commit against the merge-base**, "a CI check `red-on-parent` that cannot be bypassed by a local skip". `git grep red-on-parent 6c45f2f -- .github` returns nothing: the diff wires it only into `.agents/skills/guard/SKILL.md:50` and `.agents/skills/feature-implement/SKILL.md:147`, i.e. the local pre-push flow. The suite's own tests *do* run in CI (`bun test ./scripts/` via turbo), so the gate's behaviour is tested in CI while the gate itself is not enforced there. The design doc is committed by this PR, so this is a spec-versus-implementation gap, and the suite cannot see it.
