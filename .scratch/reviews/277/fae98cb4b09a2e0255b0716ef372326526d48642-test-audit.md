# Test audit — PR #298 (`fae98cb`)

**Verdict: grade B. Four 🔴/🟠 gaps, and one test that passes against a broken implementation.**

The two new test files are honest work — real sidecars, no mocked timers in the integration path, and the reclaim test genuinely avoids the `/health` poll that would seed the retry chain. But three of the four audit questions come back negative:

| Question | Answer |
|---|---|
| Holder closes → waiter takes the folder? | **Partly.** The waiter takes the folder after a **SIGKILL** (crashed holder), never after a **clean close** — the path the refusal page tells the owner to take and the path the commit headlines. Finding E2 |
| The bound and the give-up path asserted? | **No.** The shipped 250 ms→15 s values are unpinned (E1); the give-up path (unreadable lock ⇒ no retry) is asserted nowhere (E4) |
| Race between two waiters? | **Not covered at all** (E3) |
| Would each test fail if its fix were reverted? | **Three of four, yes** (T1 confirmed by the author's own ablation in `c12b3be`/`fae98cb`; T2, T4 by construction). **T3 no** — it asserts source-text order, so a comment carrying the same string satisfies it (Q2) |

## 1. Edge case hunter

### E1 · 🟠 The default backoff's bound is not asserted
`apps/api/src/lib/vault/reclaim-retry.test.ts:59-64`

```ts
expect(schedule[0]).toBeGreaterThan(0);
expect(schedule.at(-1]).toBe(Math.max(...schedule));
```

The test is named *"uses a first wait and a cap that cannot spin the CPU"*, but a **constant** schedule satisfies both assertions.

Triggering input: `DEFAULT_RECLAIM_BACKOFF_MS = [250, 250, 250]` (`reclaim-retry.ts:45`) → four reclaim attempts per second, forever, each one a file read plus a pid probe, against the exact "never spins the CPU" claim in the module comment. The suite stays green. So does `[250]`, and so does a 15 s first wait (which breaks the "a crashed holder is noticed right away" half of the comment).

The *shape* is only tested on an injected `[10, 20, 30]` (`reclaim-retry.test.ts:41-57`), which proves the index arithmetic, not the shipped values.

Fix — assert the values, not the shape:

```ts
expect(DEFAULT_RECLAIM_BACKOFF_MS[0]).toBe(250);
expect(DEFAULT_RECLAIM_BACKOFF_MS.at(-1)).toBe(15_000);
expect(DEFAULT_RECLAIM_BACKOFF_MS.every((ms, i, a) => i === 0 || ms <= (a[i - 1] ?? 0) * 2)).toBe(true);
```

### E2 · 🟠 The "holder closes" sequence is never exercised
`apps/api/src/lib/vault/lock.integration.test.ts:296` (`hardKillAndWait(holder)` → `SIGKILL`)

`c12b3be`'s headline is *"let a refused start take the folder once the other copy **closes**"*, and the page it serves says *"أغلق النسخة الأخرى فقط"* — close the other copy. The test proves the other story: the holder **crashed** and left a stale record.

That is a different branch of `acquireVaultLock` (`apps/api/src/lib/vault/lock.ts:594-620`):
- **crash (tested):** `EEXIST` → read the record → pid gone → settle 200 ms → `reclaimStaleLock` (rename aside, verify, unlink) → retry → `wx` create.
- **close (untested):** the exit hook (`lock.ts:553-560`) unlinks `vault.lock` → the waiter's next tick sees `ENOENT` → `openSync(lockPath, "wx")` succeeds on the **first** attempt of the acquire loop. The EEXIST branch is never entered.

Triggering input: the holder exits cleanly (SIGTERM, or the owner quits the app) and the exit hook fails to unlink the record — a broken `release()`, a swallowed unlink error, a Windows sharing violation. The waiter then blocks on the stale path for a whole staleness window. Nothing in this diff fails, because the only waiter test kills the holder the hard way.

Fix: one more case in the same file — terminate the holder with SIGTERM (guard with `process.platform !== "win32"`, the precedent is at `lock.integration.test.ts:467`), assert `vault.lock` is gone right after the exit, then assert the waiter takes the folder within the backoff window.

### E3 · 🟠 Two waiters racing for the same folder: no coverage
No test in the diff starts two refused sidecars.

Triggering input: the owner opens the app twice (or the desktop shell spawns a second copy) against one holder, then the holder dies. Both waiters tick inside the same backoff window and both call `acquireVaultLock` on the same stale record. Exactly one must win; the loser must keep serving the refusal, must **not** delete the winner's `vault.lock`, and must not publish a port record.

The module's own machinery is well covered at the unit level (`lock.test.ts:584-618`, "refuses instead of deleting a replacement lock when the stale file changes hands mid-reclaim"), but the **composition** this PR introduces is not: the per-attempt `refusalError = error` refresh (`main.ts` head, `reclaimUntilOwned`'s `attempt`), the loser's story update, and the loser's `portPublished === false` → no reconcile. A regression in any of those three is invisible.

Fix: start a second refused sidecar in the existing reclaim test; after the holder dies, assert exactly one of the two owns `vault.lock`, that the other still answers 503 with `VAULT_LOCKED_BY_OTHER_INSTANCE`, and that the loser's `vault.lock` was not deleted.

### E4 · 🟠 The give-up path (an unreadable lock) is asserted nowhere
`apps/api/src/main.ts` (head) routes the two refusals differently:

```ts
if (error instanceof VaultAlreadyLockedError) { refused = true; refusalError = error; }
else if (error instanceof VaultLockUnreadableError) { await serveLockRefusal(config, error); }  // no retry
```

That **selection** is new in this diff and has no test. `lock.test.ts:1561` covers the unreadable *page* at the unit level; nothing covers the branch in `main.ts` that decides between "retry forever" and "give up".

Triggering input: make `vault.lock` a **directory** in the data dir → `fs.readFileSync` throws `EISDIR` (not `ENOENT`) → `readOwnerOnce` classifies it `unreadable` → `acquireVaultLock` throws `VaultLockUnreadableError` → the api must serve the standalone Arabic page (`تعذّر قراءة ملف القفل في مجلد البيانات`) and must **not** start a retry loop. If the branch regressed to the generic `else` (`process.exit(1)`) or to the retry path, no test in this diff fails. The third state the commit message lists as distinct — *unreadable during a retry* — is likewise untested.

### E5 · 🟡 `attempt()` may throw, and nothing guards or pins that
`reclaim-retry.ts:29-30` states the contract (*"Must not throw: report failure as `ok:false`"*) but `runAttempt` (`reclaim-retry.ts:120-138`) has no guard: a throw escapes the timer callback and kills the refused sidecar. `main.ts` catches everything today, so this is latent, not live. Either guard it in `runAttempt` or add the test that pins the contract — right now the contract is enforced only by the caller's diligence.

### E6 · 🟡 `start()` idempotence is unpinned
`reclaim-retry.ts:78-81` (*"Idempotent"*) — no test calls `start()` twice. Triggering input: a second `start()` → two pending ticks → two attempts per interval. The in-flight guard does not help (they are separate ticks). One line fixes it: `retry.start(); retry.start(); expect(clock.delays).toEqual([10]);`

### E7 · 🟡 The default timer seam is never exercised
Every test in `reclaim-retry.test.ts` injects a fake `schedule`/`cancel`, so the production path (`reclaim-retry.ts:60-70`: `setTimeout` + `native.unref?.()`, and `clearTimeout` in the default cancel) has zero coverage. Triggering input: drop the `unref?.()` → the refused sidecar's pending tick keeps the process alive at shutdown and the app never exits. Nothing in the suite notices. One test with a 1 ms backoff and the real seam would catch it.

### E8 · 🟡 "While refused it writes nothing" is claimed, not tested
`c12b3be` claims the O_EXCL create fails against a live holder *before* the settle/rename path, so no temp file appears. Nothing checks it. Triggering input: a refused sidecar ticking against a live holder that wrongly renames the record aside — the owner's lock file would vanish and the owner's next heartbeat would fail-stop it. Cheap pin, inside the existing test: before killing the holder, `expect(fs.readdirSync(dir).filter((n) => n.startsWith("vault.lock.reclaim-"))).toEqual([])`.

### C1 · 🟠 `port-reconcile.test.ts` is a tautology, and the behaviour it names is untested
`apps/api/src/lib/port-reconcile.test.ts:11-14` asserts that a function returning its argument returns its argument. It can only fail if the predicate changes — never if `main.ts` misuses it.

Triggering input: `let portPublished = true` at the top of `main.ts` (instead of `false`) → the refused start reconciles at shutdown → `forgetPort()` recomputes the canonical record from the registry, which includes the owner's entry, and can delete or repoint the **owner's** `.dokan-port` while the owner is still serving. Nothing fails. The pre-existing integration test (`lock.integration.test.ts:192`) never kills the refused sidecar, so it cannot see a shutdown-time reconcile either.

Fix: kill the refused sidecar at the end of that test and assert the owner's `.dokan-port` still names the owner's port.

### C2 · 🟠 The post-reclaim port publication is unasserted, and the code silently skips it
`main.ts` (head), `onAcquired`:

```ts
if (boundPort !== undefined) void publishOwnedPort(boundPort);
```

`boundPort` is set in the server's **listen callback**, which fires asynchronously after `startServer()` returns, while `reclaimUntilOwned()` is entered immediately after. If a reclaim wins before that callback fires, `boundPort` is `undefined` and the publication is **skipped with no log and no error**: the new owner holds the folder and serves the vault gate, but the proxy keeps walking the dead port and the owner sees "server unreachable" — precisely the outcome #277 exists to remove.

No test asserts the publication after the reclaim at all, so neither the skip nor a plain removal of the `publishOwnedPort` call would be caught.

Fix: after the reclaim in `lock.integration.test.ts:274`, assert `fs.readFileSync(path.join(dir, "run", ".dokan-port"), "utf8")` names the refused sidecar's port. In `main.ts`, make the publication wait for the bind callback instead of skipping on `undefined`.

### 2.2 Diversity and duplicates
No duplicate coverage in either file. The six unit tests pin six distinct guards (index arithmetic, the default's shape, the trigger, the acquire-once rule, the in-flight guard, `stop()`). The four new integration tests are four different kinds of assertion (page content, port record, source order, end-to-end reclaim). The one case of near-duplication — the two refusal-page tests — is justified: one is the recycled-pid story, the other is the plaintext-publish path.

## 3. Quality reviewer — **grade B**

**Good:** test names carry the issue and the lens finding, which is what makes a red test diagnosable later. The comment blocks explain *why*, not *what*, and the two anti-trigger comments (`lock.integration.test.ts:54-59`, `:280-284`) are the right instinct: a `/health` poll would have seeded the retry chain and made the reclaim test pass without the automatic loop doing anything. `itHeavy` is applied to the four tests that spawn processes; the cheap source-text test correctly stays on the default budget. No floating promises; every `await` is awaited.

**Weak:**

**Q1 · 🟡 `expect(status.status).not.toBe(503)` accepts a broken instance**
`lock.integration.test.ts:321` — a 404 or a 500 from a half-swapped handler would also pass. After the reclaim the route answers 200 with `{ mode: "vault", state: "unconfigured" }` (`lib/vault/http.ts:172-187`, `lib/vault/manager.ts:169-190`). Assert the status and the state:
`expect(status.status).toBe(200); expect((await status.json()).state).toBe("unconfigured");`

**Q2 · 🟡 The shutdown-order test asserts source text, not behaviour**
`lock.integration.test.ts:262-272` reads `main.ts` as a string and compares `indexOf("reclaim?.stop();")` with `indexOf("server?.close();")`.

- **False pass (the case that matters):** the assertion is satisfied by any occurrence of the string, including a comment. Change the comment to `// reclaim?.stop(); must come first` and move the real call *after* `server?.close()` — the test passes and the Greptile P2 bug is back.
- **False fail:** a behaviour-preserving refactor fails it — renaming `beginShutdown`, moving the call into a helper (`stopReclaim()`), or dropping the `process.on("SIGINT"` marker. That marker is also load-bearing in a silent way: if it disappears, `indexOf` returns `-1` and `source.slice(start, -1)` becomes "the whole file minus its last character", so the region is no longer `beginShutdown` and the assertions pass or fail for the wrong reason.
- **Fix:** assert the behaviour — start a refused sidecar, `SIGTERM` it, assert it never published a port record and never created `vault.lock`. If the text form stays, at least strip comments and brace-match the function body.

**Q3 · 🟡 The first lock-file read can throw on a heartbeat**
`lock.integration.test.ts:289` — `JSON.parse(fs.readFileSync(lockFile, "utf8"))` is not wrapped, unlike the polling loop at `:304-312` which catches and retries. The holder heartbeats every 10 s with `ftruncateSync(fd, 0)` then `writeSync` (`lock.ts:452-460`), so a read landing in that window sees an **empty** file → `JSON.parse("")` throws → the test fails for a reason unrelated to the reclaim. Low probability, real flake. Use the same try/catch the polling loop uses.

**Q4 · 🟡 The failure message can name the wrong process**
`apiStderr` accumulates stderr from **both** children (`startApi:47-49`), so `"refused sidecar never took the folder; stderr: …"` can show the *holder's* stderr. Give each child its own buffer.

**Q5 · 🟡 The `afterEach` cleanup can leak the temp dir on Windows**
`lock.integration.test.ts:157-168` retries `rmSync` 10×50 ms and then gives up silently; a child that still holds a handle on Windows leaves the directory behind. Log the leftover path instead of dropping it.
