## Harsh critic

### Critical money claim to stress: the invariant `amount = attached + credit`

| # | Severity | Location | Finding |
|---|---|---|---|
| C1 | 5 | `apps/api/src/rpc/router.ts` `suppliersReturn` (free-standing branch, ~L800) | Free-standing return takes a user-supplied `amount` and credits the supplier account with it, while stock is reduced by `quantity` at the **current weighted-average cost**. There is **no upper bound linking `amount` to `quantity × costPrice`**, so a free-standing return can create arbitrarily large supplier credit (and, via `cashBack`, arbitrary cash out) from a token stock movement. The only guard is `cashBack <= availableCredit`, which the same call just inflated. Invoice-linked returns are naturally bounded by `quantity × line.unitPrice`; free-standing is not. Money is not *lost/duplicated*, but this is an unbounded value-entry surface. |
| C2 | 3 | `apps/api/src/rpc/router.ts` `suppliersPay` INVOICE target (~L715) | If the named invoice is already settled (`remaining = 0`), `payInvoice` returns `attached = 0`, no error is raised, and the whole amount silently becomes an untargeted credit. The user asked to pay a specific invoice and got a credit with no signal. Money preserved, intent violated. |
| C3 | 3 | `apps/api/src/rpc/router.ts` `invoicesPay` (~L1181) | The in-place purchase-payment path inserts the supplier `PAYMENT` entry with `input.amount` (full), unlike `suppliersPay` which caps via `splitAgainstRemaining`. It works today only because the preceding `applyPaymentToInvoice` conditional UPDATE rejects overpayment and throws first. If that ordering is ever refactored, the ledger could record an amount the cache refused. Fragile coupling, not a live bug. |
| C4 | 2 | `apps/api/src/store/drizzle-store.ts` `reportsDebts` aggregate (~L2017) | The per-supplier `account_balance` correlated subquery is evaluated in a `GROUP BY kind, COALESCE(counterparty_id, name)` query using a bare `invoices.counterparty_id`. SQLite allows it and the group key makes it constant, but it is an arbitrary-row dependency that a different SQL engine (or a future change to the group key) would silently break. |
| C5 | 2 | `apps/api/src/store/drizzle-store.ts` `backfillSupplierAccounts` (~L514) | Comment says "one payment entry per existing payment row"; the code inserts a single `PAYMENT` entry for the **`paid_amount` cache**. This is the safer choice, but if a legacy invoice carries `paid_amount > total_amount`, the inserted `PAYMENT` entry is uncapped while `deriveInvoicePaid`/the cache cap at total — the two can disagree and the balance is distorted by the excess. Edge/corrupt-data only. |
| C6 | 2 | `apps/api/src/store/drizzle-store.ts` `deleteParty` (~L1379) | The supplier delete guard now refuses deletion when account entries/returns exist, but still returns `"HAS_INVOICES"`, so the API surfaces a misleading reason for an account/return block. Cosmetic, not money. |
| C7 | 2 | `apps/api/src/store/drizzle-store.ts` `setup()` / `backfillCounterparties` ordering | The comment states the supplier backfill runs *after* the counterparty backfill so "typed-name purchases now have a supplier id". That means typed-name purchases are enrolled into signed accounts on upgrade, which contradicts the design text "Typed-name purchases stay invoice-based". Behavioural change worth an explicit decision, not necessarily wrong. |

No severity ≥ 7 found. **No demonstrated money-loss, double-charge, or duplicated-entry path.**

### Deliberate adversarial traces (all reconcile)

- Pay 400 on a 1000 invoice then return 500 of goods: paid cache 400, remaining 600 → debtReduction 500, credit 0; balance = 1000−900 = +100. Cache: total−paid−returnCredit = 1000−400−500 = 100 = remaining ✓.
- Fully-paid invoice, return 300 → debtReduction 0, credit 300, balance −300; `cashBack` up to 300. Cash-back 300 returns balance to 0 and consumes the credit ✓.
- Return 300 while still owing 1000: balance 700, `availableCredit = max(0,−700) = 0`, so any `cashBack > 0` is rejected ✓ — the "return reduces debt *and* take cash" double-dip is correctly blocked.
- Overpay via OLDEST: `allocateOldestFirst` caps at each remaining; `credit = input.amount − attachedTotal` uses **fresh** `attached` sums, so even a stale plan cannot drop money (the prior-round fix holds) ✓.
- Backfill re-entry: marker + `NOT EXISTS(... kind='PURCHASE')` + single `BEGIN IMMEDIATE` tx → no double charge even if the marker is lost ✓.

## Verdict

- **No blocker.** Money arithmetic is conserved, transactions are atomic and guarded, backfill is idempotent, and the reconciliation identity `total − paid − returnCredit = remaining` holds for purchase returns.
- Highest-signal issues are **C1 (medium: unbounded free-standing return value → unbounded supplier credit/cash-back)** and **C2/C3 (low: intent-vs-credit and fragile ordering)**. C1 is the one I would pre-register as a product decision, not a code defect.
- Tests: 23/23 pass. Coverage of the money invariants is good at the pure and store layers; no e2e run performed in this review (Playwright spec added but not executed here).

## Residual risks

- C1 unbounded free-standing return amount (no `amount ≤ quantity × cost` cap).
- C2 silent credit when an INVOICE target is already settled.
- C3 full-`input.amount` ledger entry in `invoicesPay` relies on the conditional UPDATE running first.
- C4 SQLite bare-column-in-GROUP-BY dependency in `reportsDebts`.
- C7 typed-name purchases may be enrolled into accounts on upgrade contrary to the design text.
