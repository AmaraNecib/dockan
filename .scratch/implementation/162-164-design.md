# #162 + #164 (customer half) — amount-or-percentage input + settle in place

Tier: **High-assurance** (invoice/debt money math). Base: `origin/develop` @ `54a754b`.
Branch: `feat/162-amount-percentage`.

## Problem

Two tickets that share one primitive:

- **#162** — wherever an amount is a *share of a known reference*, the owner wants to
  type either the amount or a percentage, with each recomputing the other. The app already
  has this shape twice (invoice discount, line price override) as bespoke markup. It needs
  one shared component.
- **#164 (customer half)** — the customer detail page needs an unpaid-only view and a
  «دفعة» action that settles the customer's unpaid invoices **without leaving the page**,
  using the #162 fields and a distribution preview.

Supplier-account behaviour is **#161** and is explicitly out of scope here.

## Glossary

Add to `CONTEXT.md`:

> **Amount-or-percentage input** (مبلغ أو نسبة). wherever an amount is a share of a known
> reference (a return value, the remaining on an invoice, a year of rent), the owner may type
> either the amount or a percentage of the reference; each updates the other, and 100% is the
> default. Used only where a reference total exists.

## Design

### 1. Shared component — `apps/web/src/components/ui/amount-percentage-input.tsx`

Controlled pair; the component owns the *linking* so every consumer gets identical behaviour.

```ts
export interface AmountPercentageValue { amount: string; percentage: string }

/** whole DZD for p% of a reference; p is clamped to 0..100 */
export function amountFromPercentage(referenceTotal: number, percentage: number): number
/** whole percent that `amount` is of `referenceTotal`, clamped to 0..100 */
export function percentageFromAmount(referenceTotal: number, amount: number): number
/** digits-only whole-DZD draft → number, or null when unusable */
export function parseWholeAmount(draft: string): number | null
/** digits-only 0..100 whole-percent draft → number, or null when unusable */
export function parseWholePercentage(draft: string): number | null
```

Component props:

```ts
interface AmountPercentageInputProps {
  /** the share base. `null`/absent → the percentage field is NOT rendered */
  referenceTotal?: number | null;
  value: AmountPercentageValue;
  onChange: (next: AmountPercentageValue) => void;
  amountLabel: string;
  percentageLabel?: string;   // default t("amountPercentageLabel")
  referenceLabel?: string;    // default t("amountReferenceLabel") — shown next to the fields
  amountTestId?: string;
  percentageTestId?: string;
  amountPlaceholder?: string;
  disabled?: boolean;
  invalid?: boolean;
}
```

Rules (unit-tested):

- editing **amount**: percentage is recomputed (`percentageFromAmount`), rounded to a whole
  percent; an unusable amount draft clears the derived percentage;
- editing **percentage**: amount is recomputed (`amountFromPercentage`), rounded to whole
  DZD; a percentage above 100 is **clamped to 100** and the amount becomes the full reference;
- `referenceTotal` is shown as text next to the fields so «50%» is unambiguous;
- **no reference → one field**: when `referenceTotal` is null/undefined the percentage
  input and the reference line are not rendered at all;
- defaults (full amount / 100%) are supplied by each consumer seeding `value` from the
  reference — the component is controlled and never silently invents a value.

### 2. Consumers of the component

| Surface | File | Reference | Default amount |
|---|---|---|---|
| invoice instalment | `pages/invoice.tsx` `PaymentPanel` | `invoice.remainingAmount` | full remaining |
| return cash/debt split (CUSTOM) | `pages/invoice.tsx` `ReturnsPanel` | computed `valueTotal` | full value |
| sale initial payment | `pages/sale.tsx` | cart `total` | full total |
| purchase initial payment | `pages/purchase.tsx` | cart `total` | full total |

The existing `AMOUNT | PERCENTAGE` discount and line-override controls keep their current
behaviour and markup — migrating them is not required and would widen the blast radius.

**Expense is deliberately NOT migrated.** The expense form has no reference total: the
create form is {category, amount, note, date} and `expensesListOutputSchema` carries no
running total. There is nothing to take a percentage of, so `amount-percentage-input` is not
applied and the reference for a "six months of a year of rent" is a new concept (a
recurring/period amount) that does not exist yet. Reported as a **decisionRequest**.

### 3. #164 customer half — `pages/party-detail.tsx`

Pure helper (unit-tested, no router):

```ts
export interface DistributionLine {
  invoice: Invoice;
  applied: number; // whole DZD, 0..invoice.remainingAmount
}
/** unpaid invoices, oldest first (date → createdAt → invoice-number sequence → id),
 * greedily filled by `amount` */
export function distributePayment(invoices: Invoice[], amount: number): DistributionLine[]
export function unpaidInvoices(invoices: Invoice[]): Invoice[]
export function unpaidTotal(invoices: Invoice[]): number
```

- **Unpaid-only filter** — the invoices tab defaults to unpaid-only (`role === "customer"`
  only; supplier stays as-is for #161) and shows the unpaid total from `stats.remainingAmount`.
  Toggling shows every invoice.
- **«دفعة» action** — an inline settle panel (customer only) with the #162 fields
  (reference = the sum of the unpaid invoice remainings, so the cap and the preview
  agree), a payment method, a **distribution preview** over the unpaid invoices oldest
  first, and a confirm that loops `invoicesPay` per invoice. The payment never exceeds
  what is owed because `distributePayment` caps each line at that invoice's remaining
  and the api re-checks `PAYMENT_EXCEEDS_REMAINING` inside its write unit. No new debt
  math is invented. A mid-loop api failure halts the panel (refetch + a second confirm
  is refused) so a retry cannot re-send money already taken.

## Dependencies

- `invoicesPay` (existing) — one call per distributed invoice; the api owns the boundary.
- `customersGet` (existing) — supplies `invoices` (newest first) and `stats.remainingAmount`.
- No api/contract change is required for the customer path.

## Planned tests

Unit (`bun test` in `apps/web`):

- linked math: default full/100%, edit amount → percentage, edit percentage → amount,
  rounding, 0 and 100 boundaries, >100 clamp, no-reference single field, unusable drafts;
- `distributePayment`: oldest-first ordering, per-invoice cap, exact-total, zero amount,
  fully-paid invoices excluded, rounding of the final line;
- `unpaidInvoices`/`unpaidTotal`;
- PaymentPanel renders both fields with the remaining reference and the derived percentage;
- ReturnsPanel custom split renders the linked fields;
- party detail: unpaid filter default + toggle, unpaid total, distribution preview order.

Playwright (`tests/e2e/`):

- open a customer → «دفعة» from the page → confirm → the invoice's remaining drops;
- entering a percentage updates the amount field.

## Risks

1. **Pre-filling the initial payment with the full total** changes the default from "blank =
   full credit" to "full paid" on sale/purchase. This matches the ticket's stated default but
   is a visible behaviour change; existing unit tests that assumed a blank default are updated.
2. **Filter default ON** changes the customer invoices tab from "all" to "unpaid"; the
   existing e2e assertion (`party-invoice-row` count 2) is updated to assert the unpaid view
   and then toggle to all.
3. Multi-invoice settlement loops `invoicesPay`; a mid-loop api failure leaves earlier
   invoices paid (each is an independent atomic payment). The preview makes the intended
   allocation explicit; the error path refetches and reports the failure.
4. The linked pair is lossy by design (integer percent): editing percentage then amount can
   differ by rounding. The field last edited is the source of truth; the derived field is
   shown, never re-fed back.
