## Axis B — Standards / code quality (AGENTS.md, engineering-workflow, Fowler baseline)

### Correct

- **Money paths are transactional and boundary-guarded, not check-then-act.** `suppliersPay`, `suppliersReturn`, `suppliersRefund` each run one `withTransactionImmediate` unit; the entry is inserted and the invoice cache is moved by a conditional UPDATE that throws on boundary violation (`applyPaymentToInvoice`, `applyDebtOffsetToInvoice`). Matches the design's stated risk control.
- **Excess-to-credit cannot silently drop money after the OLDEST allocation.** The handler ignores the plan's stale `remaining` and recomputes `attached` from a fresh in-unit read; `credit = input.amount − Σ attached` (`router.ts` ~712). Evidence: the comment and the code both make the fresh read authoritative.
- **Pure math is extracted and unit-tested.** 17 tests in `supplier-ledger.test.ts` cover sign/balance, allocation ordering ties, caps, excess split, invoice derivation cap, refund cap. All pass (23/23 with the store test, 0 fail).
- **Idempotent, self-healing backfill.** `backfillSupplierAccounts` is marker-gated **and** `NOT EXISTS`-guarded, runs in one `BEGIN IMMEDIATE`, and uses `total_amount > 0` + supplier-`EXISTS` so a legacy zero-total or orphaned-counterparty row cannot abort boot or violate an FK (`drizzle-store.ts` ~517).
- **Delete guard closes a raw-FK leak.** A supplier with entries/returns is now refused (`supplierGuard` in `deleteParty`), and the web disables the delete button when the account has entries.
- **Contracts are strict.** `supplierPayInputSchema` and `supplierReturnInputSchema` `superRefine` enforce exactly-one-of target/invoice/free-standing shapes; all amounts are whole `dinarsSchema`.
- **i18n added for every new UI string** (`i18n.ts:782+`), including the `REFUND_EXCEEDS_CREDIT` error key.
- **`cell-ltr` guard updated** to the new party-detail cell count (`cell-ltr.test.ts:65`), so the #166 regression guard stays honest.

### Notes (non-blocking)

1. **`deriveInvoicePaid` is production-dead code.** `grep` finds it only at `supplier-ledger.ts:90` and in its own unit test; no store/router caller. The design (§ Pure modules) says "a store test asserts [the cache matches the entries]" on fixture data — the store test instead recomputes the sum inline. The invariant is still tested, but the exported function is decorative (Fowler: dead code; risk of the cache and the pure proof drifting apart with nothing forcing them together).
2. **Free-standing return is always credit, so a credit and unpaid invoices can coexist and are never reconciled.** `supplierReturnSplit(value, null) → {debtReduction: 0, credit: value}`. A supplier with unpaid invoice(s) plus a free-standing return shows a net balance in `/debts` and the party header while the invoice still prints its old remaining; there is no operation to apply an existing credit to an unpaid invoice. This matches the written design, but for a high-assurance money feature it is a domain gap worth an explicit decision/ADR note.
3. **Backfill diverges from the design text.** Design says "a PAYMENT entry per existing `payments` row"; implementation writes **one** PAYMENT entry equal to `invoices.paid_amount` (the cache). The code comment justifies it (a legacy invoice can carry a paid amount with no matching payment row), which is defensible, but the design doc is now inaccurate on this point.
4. **`getSupplierReturn` (port/store) is used only by the store test.** The web voucher reads `suppliersReturnsList` instead. Extra production surface with no production caller — either wire it into the voucher print path or drop it.
5. **`DELETE` refusal reuses the code `HAS_INVOICES`** (`drizzle-store.ts` `deleteParty`) even when the blocker is account entries with no invoices; the name is now misleading for credit-only suppliers.
6. **`/debts` `invoiceCount` semantics differ between the main aggregate and the credit-only supplement.** The main path counts only unpaid invoices (`WHERE remaining_amount > 0`); the `creditOnly` query counts all PURCHASE invoices (`COUNT(*) … i.kind='PURCHASE'`). Minor inconsistency in the count shown on a credit-only supplier row.
7. **Return-panel validation error is misleading.** `supplier-return-panel.tsx` throws `new Error("RETURN_EXCEEDS_RETURNABLE")` for "no lines selected" and for free-standing "item/qty/amount missing", which will surface to the user as a false cap message.
8. **Server error codes likely lack i18n keys.** Only `REFUND_EXCEEDS_CREDIT` was added; `INVOICE_NOT_PURCHASE`, `RETURN_DEBT_OFFSET_REFUSED`, `LINE_NOT_ON_INVOICE`, `RETURN_LINE_NOT_RETURNABLE` are new and rely on `tError` fallback. Unverified against the existing error-key table.
9. **Schema DDL index differs cosmetically from the design** (`(supplier_id, occurred_at)` vs `(supplier_id, occurred_at, rowid)`); harmless since rowid is implicit.
10. **Test-coverage gap for the router money paths.** No test exercises `invoicesPay` writing a supplier entry (scope item 2 "paying inside an invoice still marks it paid"), nor `suppliersPay` OLDEST multi-invoice allocation / excess-to-credit through the router, nor the cash-back cap end-to-end. The store test covers entry insert + balance + backfill only.
