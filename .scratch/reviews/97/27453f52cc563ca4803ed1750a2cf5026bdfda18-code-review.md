## Standards

**Correct (verified)**

- `RequireSession` no longer gates on the import: the gate state, its
  `LoadingScreen` branch, and the unmount-tracking closure are gone. The
  `migrationStarted` ref latches after the pending/null early-returns, so a
  later sign-in still triggers the one-time import and StrictMode cannot
  double-run it.
- The import is non-blocking and one-shot, and the shell's scanner listener
  mounts on the first authenticated render (the regression's root cause).
- The scanner gap follows the repo's documented env-injection pattern
  (`.agents/wisdom/2026-08-24-deterministic-timing-tests.md` rule 2); production
  stays at 50 ms, e2e uses 250 ms, and no existing e2e types above 12 ms.
- Storage access remains guarded; the legacy key is only cleared after a
  successful import or when the server already holds a value.

**Hard violation found and fixed in this HEAD**

- The background import wrote the server but never refreshed the shared
  preferences cache. With `staleTime: 30s` and the shell mounting first, the
  sidebar could stay on its default long after the import landed — the exact
  state the gate had (wrongly) protected against. **Fixed** `27453f5`: the
  import returns the value; `RequireSession` merges it into the cache (never
  creating a partial map) and invalidates, so the shell refetches truth.

**Judgement calls (dismissed)**

- The read-window guard does not re-check after the import's write. The check
  and the write are one synchronous block; the residual window is a few ms on a
  loopback, and the legacy fallback is retained.
- `writtenKeys` is module-global, not per user. Single-owner desktop app.
- The 250 ms e2e gap weakens editable-regime fidelity against production's
  50 ms. Accepted and documented; the unit test derives its own slow pace.
