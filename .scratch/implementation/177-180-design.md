# Design — #177 supplier account server hardening + #180 display/parsing

Base: `origin/develop` @ `8259667`. Tier: **High-assurance** (invoice/debt money math).
Branch: `feat/177-180-supplier-hardening`.

## Problem

#177: #176 shipped a UI-level guard around a تسوية (manual supplier adjustment). A
non-UI caller can still (a) write an adjustment whose invoice linkage is not applied
to the invoice (the account entry and the invoice's `remainingAmount` diverge), and
(b) submit the same adjustment twice (a network/script retry double-posts).

#180: (1) the `/debts` supplier group total can be a net credit; it renders a bare
negative number instead of the dashboard's «رصيد لنا عند الموردين» credit label.
(2) `parseBulkAmount` (bulk opening balance) accepts `1 000` / Arabic grouping and
rejects `1 000,00`; the single-entry money inputs use a separate digits-only reader,
so the same string means different things in two places.

## #177 design

### Server invariant: all adjustments go through one guarded store method

Add `StorePort.insertSupplierAdjustment(input): Promise<SupplierAccountEntry>`:

```ts
type SupplierAdjustmentInsert = {
  supplierId: string;
  direction: "WE_OWE" | "THEY_OWE";
  amount: number;             // whole DZD, > 0 (contract-enforced)
  reason: string | null;
  occurredAt: string;         // changeset signature part
  invoiceId: string | null;   // null = account-only, non-null = linked reduction
  ref?: string | null;
};
```

Inside one caller-owned `BEGIN IMMEDIATE` unit the method:

1. **Transaction required** — it refuses to run when `conn.inTransaction` is
   false (`OUTSIDE_TRANSACTION`), because outside the unit the duplicate check
   races and the entry could commit without its reduction. The router always
   wraps in `withTransactionImmediate`.
2. **Amount re-validated** — a non-contract caller must not pass a negative or
   fractional amount (`INVALID_AMOUNT`); a negative amount would make the
   conditional UPDATE *increase* the invoice's remaining.
3. **Duplicate signature** — `SELECT` an existing `ADJUSTMENT` for the same
   `(supplierId, direction, amount, note, invoiceId, occurredAt)`; if one exists it
   throws `SupplierAdjustmentError("DUPLICATE")` before any write. `invoiceId` is
   part of the key so an account-only and a linked adjustment of the same shape
   are distinct. When the caller omitted `occurredAt` the router forwards
   `serverStamped: true` and the signature drops `occurredAt` (matches any time),
   so a retry that gets a fresh server clock cannot double-post. `reject` (not
   `normalise`) is chosen because the ledger is append-only: silently returning the
   old entry would hide a real collision, while an explicit conflict is auditable.
4. **Direction/link coherence and ownership** — a linked adjustment must be
   `THEY_OWE` (`LINKED_DIRECTION`), and the named invoice must be a `PURCHASE`
   belonging to this supplier (`INVOICE_MISMATCH`), so a non-UI caller cannot
   credit one supplier while reducing another's invoice.
5. **Atomic linkage** — for a linked adjustment it runs the shared conditional
   `applyDebtOffset` (the same predicate `applyDebtOffsetToInvoice` uses) and
   throws `SupplierAdjustmentError("EXCEEDS_REMAINING")` when 0 rows change, so
   the entry and the reduction cannot diverge (both inside the same unit; the
   caller's rollback is the failure path).
6. Account-only (`invoiceId === null`) inserts `invoice_id = NULL` and never
   touches any invoice.

`insertSupplierEntry` gains a hard guard: an `ADJUSTMENT` with a non-null `invoiceId`
is refused (`LINKED_NEEDS_ATOMIC_PATH`). Only `insertSupplierAdjustment` can write a
linked adjustment, and it always attempts the reduction. Account-only raw inserts stay
allowed for low-level test setup; the RPC layer routes both shapes through the guarded
method. `applyDebtOffsetToInvoice` is unchanged (still used by returns).

### Router

`suppliersAdjust` and `suppliersOpeningBalances` call `tx.insertSupplierAdjustment`
instead of `tx.insertSupplierEntry` + a separate offset. `SupplierAdjustmentError` maps
to ORPC errors: `DUPLICATE` → `CONFLICT`/`DUPLICATE_ADJUSTMENT`, `EXCEEDS_REMAINING` →
`BAD_REQUEST`/`ADJUSTMENT_EXCEEDS_REMAINING`, `LINKED_DIRECTION` →
`BAD_REQUEST`/`ADJUSTMENT_INVOICE_DIRECTION`, `INVALID_AMOUNT` →
`BAD_REQUEST`/`ADJUSTMENT_INVALID_AMOUNT`, `OUTSIDE_TRANSACTION` →
`INTERNAL_SERVER_ERROR`/`ADJUSTMENT_NOT_TRANSACTIONAL`, `INVOICE_MISMATCH` →
`BAD_REQUEST`/`INVOICE_NOT_PURCHASE`. The bulk batch also rejects a
duplicate `(supplierId, direction, amount)` row and a duplicate new-supplier name up
front (`CONFLICT` / `DUPLICATE_OPENING_BALANCE_ROW`) so the whole batch does not roll
back on a vague code and no duplicate party is created. All refusal codes have Arabic
i18n entries. The router's friendly pre-checks (invoice ownership, `amount >
remaining`) stay for clearer errors; the store is the backstop, and it re-checks
owner, kind, and supplier too.

### Invariants and tests

- account-only entry never carries an `invoiceId` (store test + existing router test);
- linked entry always reconciles entry + remaining, and a duplicate linked retry does
  not reduce twice (router tests; store test through the atomic method);
- duplicate account-only submission posts once (router test: second is
  `DUPLICATE_ADJUSTMENT`, one entry, balance moved once).

## #180 design

### One grouped-amount parser

New `apps/web/src/lib/amount-parse.ts` owns the low-level readers:

- `parseWholeAmount` (moved from `components/ui/amount-percentage-input`)
- `parseWholePercentage` (moved)
- `parseGroupedAmount` (moved from `parseBulkAmount`): plain digits or valid 3-digit
  grouping (comma/space/Arabic thousands), Arabic-Indic digits, rejects decimals and
  malformed separators.

`components/ui/amount-percentage-input.tsx` re-exports `parseWholeAmount` /
`parseWholePercentage` (public API unchanged) and its `amountEdited` amount side uses
`parseGroupedAmount`, so the shared single-entry money field accepts the same grouped
strings as the bulk screen. `lib/supplier-opening-draft.ts` drops its local copy and
uses `parseGroupedAmount` (keeping the bulk row readers). The adjust panel and the
other money-draft readers (settle/pay/refund panels, sale/purchase/invoice paid-now)
use `parseGroupedAmount` for the amount side so field and submit agree. Quantity
readers keep `parseWholeAmount` (a quantity is not a grouped amount).

### /debts credit label

`DebtGroup` takes an optional `creditLabel`. When the supplier group total is negative
it renders `creditLabel: |total|` (matching `dashboardSupplierCredit`) instead of
`الإجمالي: total`. Customer group totals are always ≥ 0, so only the supplier group
passes the label. i18n reuses the existing `dashboardSupplierCredit` string.

### Tests

- `lib/amount-parse.test.ts`: grouped parser accepts/rejects table plus agreement
  assertions on tricky strings (including overflow and mixed-script grouping).
- `supplier-opening-draft.test.ts`: the bulk row readers wire to the shared parser.
- `supplier-adjust-panel.test.tsx` / `amount-percentage-input.test.tsx`: `1 000`
  parses to 1000 in the single-entry money field.
- `debts.test.tsx`: a negative supplier group total shows the credit label and the
  absolute amount; a positive or exactly-zero one shows the plain total.
- Grouped-input assertions for every other single-entry money reader
  (`settleAmountError`, `paymentAmountError`, `customCashError`, `saleDebt`,
  `parseCashBackDraft`, and the expenses amount).
- `tests/e2e/supplier-adjustment.spec.ts`: a net-credit supplier shows the
  «رصيد لنا عند الموردين» label on the `/debts` group total.

## Risks

- Rejecting same-signature adjustments could block a legitimate intentional second
  entry in the same second; mitigated by explicit confirmation UX in bulk and by the
  append-only "record another with a different reason/date" path.
- Moving parsers must not change quantity parsing; quantities keep `parseWholeAmount`.
- `insertSupplierEntry` guard could break direct store tests; only the one linked
  adjustment store test changes (to the atomic method).

## Greptile round 1 (PR #182) — retry idempotency

Greptile flagged three findings; all fixed with pre-fix-failing tests.

- **`newSupplierName` lost-response resend.** A resend minted a second supplier via
  `createParty`, so the signature dedup ran under a fresh id and double-posted. The
  bulk handler now resolves a typed name to an existing supplier
  (`normalizeTextKey`, the picker's fold) before creating one. When two suppliers
  fold to one name (legacy corruption), it prefers the entry-carrying party, then the
  lowest id, so a resend reaches the first attempt's row. The name map is built
  lazily only when a row uses `newSupplierName`.
- **Linked resend reported the wrong reason.** The router ran
  `amount > remaining` before the store's duplicate check, so an exact resend of a
  reduced (or zeroed) invoice reported `ADJUSTMENT_EXCEEDS_REMAINING`. The router
  pre-check is removed; the store dedups first and its conditional offset still
  refuses a genuinely oversized link. The duplicate check therefore owns the error.
- **Credit-label e2e too weak.** It now also asserts the group total carries no minus
  sign.
- **Confirmation gate symmetry.** A `newSupplierName` that resolves to an existing
  supplier with entries now requires `confirmExisting`, exactly like the
  `supplierId` path, EXCEPT when the exact signature already exists (a resend), which
  the guarded write reports as `DUPLICATE_ADJUSTMENT`. `StorePort.hasSupplierAdjustment`
  exposes the one signature condition builder so the gate and the write cannot drift.

The retry path is therefore idempotent end-to-end for both opening-balance shapes:
`newSupplierName` and `supplierId`, confirmed or not, and for linked and account-only
adjustments.

## Greptile round 2 (PR #182) — named-supplier confirmation race

When the typed supplier is created (with history) after the page loaded, the bulk
save returns `OPENING_BALANCE_EXISTS` and opens the confirmation dialog. The
dialog's `save(true)` only confirmed rows that already carried an existing id, so
after the list refresh turned the typed name into a duplicate the save returned
without sending anything and the row was dropped.

The page now matches the typed name to an existing supplier with `normalizeTextKey`
(the server's fold) and moves the draft onto that supplier's row, preserving amount
and direction:

- a `useEffect` adopts as soon as the match exists AND the name field is not
  focused (so an owner still typing an intended new name, with the amount entered
  first, is not cut off mid-word);
- `save()` keeps a synchronous fallback (a same-tick save before the effect commits)
  so the row can never be dropped.

The duplicate-name error is removed — the row moves instead. A matching typed name
auto-moves once the field blurs. Both orderings are covered: the match arriving
before the save, and the match arriving with the `OPENING_BALANCE_EXISTS` refusal.

Refinements from the delta reviews:

- the adoption effect runs only when BOTH the name and amount fields are unfocused,
  so a multi-digit amount is never moved mid-keystroke (the name-only gate moved a
  partial `1500` as `1`);
- the client tie-break mirrors the server's (entry-carrying party, then lowest id);
- a typed name that resolves to a supplier which already has a filled row is a
  conflict, not a second entry: submit/save block with `supplierOpeningRowHasAmount`,
  so one batch never posts two opening balances for one supplier;
- a focused duplicate name submitted with Enter counts as the resolved row instead
  of reporting “nothing entered”.

## Out of scope / deferred

- **Client idempotency key** (debate finding 1 residual): the guard keys on the
  request signature as #177 specifies. A caller that omits `occurredAt` is protected
  by the server-stamped wildcard, but a caller that sends a *changing* timestamp for
  the same logical retry is not. A durable fix is an explicit client-generated
  idempotency key on `supplierAdjustInputSchema`, stored with the entry; follow-up.
- DB-level unique index for the signature (the `BEGIN IMMEDIATE` lock already
  serialises writers; a partial unique index would need a schema-version bump).
- Customer-side accounts (ADR-0010 extension path).
- Consolidating the copy-pasted amount↔percentage sync effect shared by the six
  settle/pay/refund/invoice/sale/purchase panels.
- Collapsing the duplicated opening-balance confirmation gate (three lines in the
  `supplierId` and `newSupplierName` branches) into one helper, and a names-only
  supplier lookup instead of `listParties`' per-party aggregates.
