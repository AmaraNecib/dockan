## 1. Probe (a) — `CURRENT_SCHEMA_VERSION = 2` refusal + migration test gaps

### Critic
**C1 — severity 3 — `apps/api/src/lib/schema-version.test.ts:136-155`: the upgrade path v1 → v2 is untested.** The new test seeds `PRAGMA user_version = 2` and asserts a *build limited to v1* (`assertSchemaVersionSupported(handle, 1)`) throws. That proves the gate math (`found > supported`, `schema-version.ts:47-52`) but never exercises the scenario the bump creates for every existing install: a database stamped `user_version = 1` (pre-#161, no supplier tables) opened by the new build, migrated forward, re-stamped to 2. The only forward-migration test (`schema-version.test.ts:~190`) starts from version **0**, not 1. The exact "v1 user upgrades" path has no end-to-end test and no assertion the supplier tables get created / version advances to 2.

**C2 — severity 2 — `apps/api/src/store/drizzle-store.ts:543-549`: the bump's premise is only partly true, because setup self-heals.** The commit message and `schema-version.ts:10-14` claim a v1 build "would record purchases and payments with no supplier entries and silently corrupt the balance." But `store.setup()` runs a boot backfill inserting a `PURCHASE` entry for every `kind='PURCHASE' AND counterparty_id IS NOT NULL AND total_amount > 0` invoice lacking one (`:549`). Supplier *payments* did not exist before #161, so the only thing a v1 build could write is a purchase invoice — which the backfill reconstructs. The bump is defensive rather than strictly load-bearing; harmless and defensible, but the stated justification overstates the corruption risk.

**C3 — severity 1 — `schema-version.test.ts:143-153`: literal `2` duplication.** Hardcodes `user_version = 2` / `toBe(2)` instead of deriving from `CURRENT_SCHEMA_VERSION`; a future bump keeps the test passing while testing nothing about the new edge.

### Defender (confidence 9)
- The gate runs at every entry point: `db/connection.ts:73`, `main.ts:231`, `db/encrypted-connection.ts:318`, and re-checked under a write lock in `stampSchemaVersionLocked` via `drizzle-store.ts:1054`. No path writes entries-less money.
- The migration is additive (`CREATE TABLE IF NOT EXISTS` + columns); the boot backfill is the migrator.
- C1 is coverage, not correctness — it is a strict superset of the tested v0→current path.
- C2 does not make the bump wrong; over-refusing an incompatible writer is the conservative ADR‑0008 §4.5 choice.

## 2. Probe (b) — zero-amount money paths

### Critic
**C4 — severity 2 — `apps/api/src/rpc/router.ts:838-852` (new test `supplier-account-zero.test.ts`): the zero-value *return* path is untested.** Fix #8 newly lets the UI submit an invoice-linked return of free goods (`supplier-return-panel.tsx` `invoiceReady` branch), i.e. `amount = 0`. Server-side this is safe — `supplierReturnSplit(0, remaining)` yields `{0,0}` and the three guarded inserts (`router.ts:838/845/851`) are all skipped, so the ledger `CHECK (amount > 0)` is never touched. But **no server test covers it**: `supplier-account-zero.test.ts` only exercises the zero-total *purchase*, and the panel test mocks the RPC (`supplier-return-panel.test.tsx:26-33`). A future `>= 0` refactor would regress silently.

**C5 — severity 1 — `supplier-ledger.ts:36-40`: `supplierChargeEntryAmount` returns null for negatives too.** `totalAmount > 0 ? totalAmount : null` treats a corrupt negative identically to zero — deliberately safe (a negative entry would corrupt the balance even if CHECK allowed it). Tests assert both (`supplier-ledger.test.ts:151-156`). No issue; logged for explicitness.

### Defender (confidence 9)
- Both legs guarded: charge skipped when `charge === null` (`router.ts:1115-1124`), payment leg gated by `if (paidAmount > 0)` (`:1125-1130`). A total‑0/paid‑0 purchase opens no entry while invoice + stock intake commit — proven end-to-end by `supplier-account-zero.test.ts` (`totalAmount === 0`, `remainingAmount === 0`, `stockOnHand === 3`, `balance === 0`, `entries.length === 0`).
- The return side is safe by construction: each insert sits behind a strict `> 0` guard, so a zero return cannot reach the CHECK-protected table.
- C4 is a coverage gap only; runtime behaviour is correct today.

## 3. Probe (c) — preview-vs-server parity

### Critic
**C6 — severity 2 — `apps/web/src/components/parties/supplier-pay-panel.tsx:92`: preview reads a possibly stale `invoices` prop.** The fix replaces `Math.min(amount, owed)` with `distributePayment(invoices, amount)`, now algorithmically identical to the server's `allocateOldestFirst` (`supplier-ledger.ts:71-90`): same filter (`remaining > 0`), same 4-key ordering (invoiceDate → createdAt → numeric sequence → id), same per-invoice cap, same `Math.floor`. Parity holds for the *same input*, but the preview runs on the client cache while the server re-reads fresh in-transaction (`router.ts:718-733`). Under a concurrent payment the preview can disagree with what is persisted — pre-existing, and the server's fresh-read credit computation (`router.ts:721-723`) ensures no money is dropped, but the preview is not guaranteed byte-accurate.

**C7 — severity 1 — `supplier-pay-panel.tsx:92`: `invoices` is passed wholesale; server filters to `kind='PURCHASE'`.** `distributePayment` filters only on `remainingAmount > 0`; the server uses `listOutstandingPurchaseInvoices` (`router.ts:719`). If the panel were ever handed a non-purchase invoice with a balance, the preview would over-distribute. Today the prop is purchase-scoped — latent coupling, not a live bug.

### Defender (confidence 9)
- The original bug (capping at `owed`, inventing credit) is definitively fixed: 900 fills a 1000 invoice even when `owed = 800`, and `credit = amount - distributed` yields `0`. Both new tests pass (`supplier-pay-panel.test.tsx:74-96`), including 1200 → 1000 applied + 200 credit.
- Parity is exact, not "close": `distributePayment` (`party-settle.ts:31-55`) and `allocateOldestFirst` share the same 4-key sort and `Math.min(remaining, left)` loop.
- C6 is a UI-staleness nit backstopped by the server's fresh reads; C7 is guarded by usage.

## 4. Probe (d) — printed voucher (name + free-standing unit price)

### Critic
**C8 — severity 2 — `router.ts:814` / `supplier-return-print.tsx:85-95`: presentation-only fix; stock cost still persisted as `unitCost`.** For FREE_STANDING the server stores `unitCost: item.costPrice` while `amount` is the agreed return value. The voucher now prints `—` for FREE_STANDING (`supplier-return-print.tsx:88-92`, verified by the "not.toContain('999')" assertion), but the leaked stock cost still travels in `SupplierReturnRecord.lines[].unitCost` JSON from `suppliersReturnsList`/`getSupplierReturn`. The storage model conflates "stock cost at return time" with "agreed unit price"; the display hack hides the symptom rather than separating the fields.

**C9 — severity 1 — `supplier-return-print.tsx:68-70`: `supplierName ?? supplierId` fallback.** The join is a LEFT JOIN (`drizzle-store.ts:1744/1783`) so `supplier_name` can be null; the fallback prints the raw UUID. In practice `supplierId` is a NOT NULL FK to a live row, so null should be unreachable — defensive, logged for completeness.

### Defender (confidence 9)
- Supplier identity is joined at the correct seam: `drizzle-store.ts:363-367` maps `supplier_name` in `toSupplierReturn`; list and detail queries add `leftJoin(suppliers, ...)` (`:1744`, `:1783`). The contract now requires the field (`core.ts:628`), so all construction sites are type-checked; the store test asserts "مورد مرتجع" round-trips (`supplier-account-store.test.ts:148-149`), the print test asserts "شركة الأمل", and `returns.tsx:221` surfaces the name in global history.
- The free-standing unit-price suppression is correct and tested: stock cost 999 is provably absent from the voucher's unit cell.
- C8 is a modelling nit with no shipped-UI defect; C9 is defensive and unreachable.
