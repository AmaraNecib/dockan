## Axis 2 — Spec (Greptile round-2 finding + issue #161 scope)

### Finding 1 — "the hidden invoice draft must not warn in free-standing" → CORRECT

- Root cause is real and confirmed in code: switching mode does **not** clear `quantities`
  (only changing the invoice does, panel :148). So after typing an invalid invoice quantity
  (`1.5`), `quantities.l1` survives the switch to free-standing, `invoiceReady` stays false,
  and `quantityDraftInvalid` (panel :70) stayed `true` — the panel warned about a draft that
  is not rendered and not submitted.
- Fix at `supplier-return-panel.tsx:235` gates that term on `mode === "INVOICE_LINKED"`.
  In free-standing the warning is gone (test.tsx:182-199), while the value is still retained
  in state, so **switching back to invoice-linked re-shows it** — the gate re-enables on mode
  change and `disabled` at :248 again requires `invoiceReady`. Consistent both directions.
- Truthfulness: `submit()` in free-standing (panel :90-103) reads only `itemId`, `quantity`,
  `amount`, `cashBack` and never touches `quantities`. Suppressing the warning therefore
  matches what is actually sent — no draft is silently dropped by this change.

### Finding 2 — "`cashInvalid` stays shared" → CORRECT

- The expression keeps `|| cashInvalid` **outside** the mode predicate, so a malformed
  cash-back still warns in free-standing (panel :235). Regression test at test.tsx:201-207
  covers it with the mode switched to free-standing first; it passes.
- Both the warning (:235) and the submit button (:247) still use the same `cashInvalid`, so
  the "warn but allow" / "block but silent" mismatch does not exist for cash-back.

### Cross-check — submit `disabled` still matches the gate → CORRECT

- `disabled` (panel :244-249) = `submitting || create.isPending || cashInvalid ||
  (mode === "INVOICE_LINKED" ? !invoiceReady : value <= 0 || itemId === "")`.
- Invoice-linked: warning shown iff `!invoiceReady`; button disabled iff `!invoiceReady` (plus
  shared `cashInvalid`). Exact match.
- Free-standing: the hidden invoice draft affects neither the warning nor `disabled`; the
  button is driven by `cashInvalid`, `value <= 0`, `itemId === ""`. Exact match with the new
  gate. This is the property the round-2 finding was really about, and it now holds.

### Regression test quality (spec evidence)

- `test.tsx:182` asserts the *before* state (warning present at `1.5`), the *after* state
  (warning `toBeNull()` immediately after the mode switch), *and* the payload actually
  submitted (`{ supplierId, itemId, quantity: 2, amount: 300 }`). It therefore falsifies both
  the stale-warning bug and any "suppressed warning but still blocks submit" regression.
- The test is genuinely discriminating: with the pre-`0e56e48` gate, `quantities.l1 = "1.5"`
  survives the mode switch, so the `toBeNull()` at test.tsx:188 would fail. The commit's
  "verified the test fails without the one-line fix" claim is consistent with the state
  semantics in the component. (Not re-run as a mutation check — source is read-only for this
  review; see residual risks.)

### Non-goals not regressed

- Only the warning gate changed; `parseReturnQuantities` / `parseCashBackDraft`
  (`supplier-return-draft.ts`) are untouched, so the "reject, never silently drop" invariant
  for invoice-linked drafts is intact (tests at test.tsx:145-165 still pass).
- Invoice-linked, free-standing, cash-back, and submitted-payload behaviours all remain
  asserted by the full file; the `itemsList` mock change only adds a selectable item and does
  not weaken any pre-existing assertion.
