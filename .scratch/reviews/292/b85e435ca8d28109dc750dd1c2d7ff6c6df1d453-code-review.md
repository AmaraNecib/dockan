## Standards

**S1 — Blocker (wisdom `vault/gate-every-write-site`: "write a test per site… a flag checked at four of six sites is indistinguishable from a flag checked at zero until you do").** The new rule is "one log line per replacement, whichever site notices it", and the wisdom lesson applies to it directly. Three of its sites are unpinned, by inspection of `fence-heartbeat.test.ts`:

- `recordDiskStamp("write")` is called at two write sites: `persistNow` (`apps/api/src/db/encrypted-connection.ts:478`) and `checkpoint` (`:551`). Only the first is pinned. Removing the `checkpoint` call at `:551` leaves all five tests green: `checkpoint()` evaluates `snapshotIsCurrent()` (`:550`) first, and `diskFenceIsMine()` (`:409`) logs the same event with the same `"write"` wording, so the assertion at `fence-heartbeat.test.ts:177` still sees exactly one event.
- `noteDiskStamp(fence.stamp, "write")` inside `diskFenceIsMine()` (`:409`) is pinned by nothing either — `recordDiskStamp` (`:364`) already reports the same event from both write sites, so removing `:409` also leaves all five tests green.
- The ordering the spec headlines — "the heartbeat names it, the rest stay quiet" — is unpinned. `fence-heartbeat.test.ts:106` asserts `expect(events).toEqual(["VAULT_SNAPSHOT_FENCE_FOREIGN"])` **before** the persist at `:110` and never re-asserts `events` after it, so a second line from the write path for the same theft is invisible. Trigger: heartbeat names the theft, then `conn.persistIfDirty()` at `:110` logs a second `VAULT_SNAPSHOT_FENCE_FOREIGN`; the test passes.

Commit `b85e435`'s body claims "the write sites are enumerated (persistNow, checkpoint) and each is pinned" — the checkpoint site is not, and the `diskFenceIsMine` report is not.

**S2 — Blocker (a false theft report on a retried first-run setup).** `apps/api/src/main.ts:231-232` sets `seedBytes` whenever `input.fresh` and the legacy plaintext exists, and `:241-242` then sets **both** `storeInput.fresh` and `storeInput.seedBytes`. In `apps/api/src/db/encrypted-connection.ts:252` the `seedBytes` branch is taken **first**, so the `fresh` branch that deletes the orphan snapshot (`:281`, `fs.rmSync(snapshotPath)`) never runs — the orphan of the interrupted attempt survives, carrying the *previous* process's lock token (`apps/api/src/lib/vault/lock.ts:426`, `token: randomBytes(16)`). The first write's `recordDiskStamp("write")` (`:478`) then reads that orphan as another writer's envelope: `observedStamp` is still `undefined` (the seed path never calls `noteDiskStamp` at open), so `noteDiskStamp` (`:343-349`) reports it — one false `VAULT_SNAPSHOT_FENCE_FOREIGN` per retried setup, worded "another writer's envelope replaced the snapshot on disk: the version this holder acknowledged is not on disk". Trigger: upgrade-to-vault on a machine with a legacy plaintext DB, where the first setup attempt dies after `conn.flush()` and before `commitSetup()` — the exact window the repo already models in `apps/api/src/lib/vault/gate.test.ts:801` ("keeps first-run setup retryable when the bootstrap fails after the snapshot landed (round-7 finding 1)"). The retry is a supported path (`apps/api/src/lib/vault/http.ts:222-224` calls `deps.manager.abortSetup()` so "a retry starts clean"). Before this diff, no such line existed.

**S3 — Blocker (one replacement, two log lines, when a setup is retried).** `apps/api/src/main.ts:262` calls `vaultLock?.addHeartbeatCheck(() => conn.recheckFence())`. `bootstrapVault`'s catch closes the failed connection (`main.ts:341-343`, `if (!lockLost) await conn.close()`), but the lock keeps the check forever — `lock.ts:220-222` has no removal API and `release()` (`:596-608`) does not clear the array. The HTTP setup route allows a retry of a failed setup (`http.ts:222`), so `bootstrapVault` runs again (`appReady` is still `false`), a second connection is created, and a **second** check is registered on the same lock. Both connections keep their own `observedStamp`, so a replaced snapshot is reported by both: two `VAULT_SNAPSHOT_FENCE_FOREIGN` lines for one replacement — the one thing the change exists to prevent — and the fence is read twice per tick.

**S4 — Major (the unfenced mode now logs a FOREIGN it never logged).** `recordDiskStamp` (`:362-365`) has no `connectionStamp === undefined` guard, while `recheckFence` (`:458`) and `diskFenceIsMine` (`:404`) both have one. Trigger: `createEncryptedConnection` without `writeStamp` (the documented unfenced mode, `encrypted-connection.ts:96-106`: "Absent = unfenced: the legacy envelope is written and read, exactly the pre-#280 behaviour") over a `dokan.db.enc` that carries a stamp → the first write's `recordDiskStamp` reads `outcome: "fence"`, `stamp !== undefined` → `noteDiskStamp` logs `VAULT_SNAPSHOT_FENCE_FOREIGN` (`:349`) against a connection that has never been fenced. Pre-#280 behaviour was silence. Not reachable from `main.ts` (it always passes `writeStamp`), but it breaks the module's own documented contract.

**S5 — Major (unbounded warning on the heartbeat, and a forced rewrite it did not force before).** `recheckFence`'s unreadable branch (`encrypted-connection.ts:466-469`) warns on **every** tick — the dedupe in `noteDiskStamp` only covers the `"fence"` outcome — and then sets `fenceSatisfied = false` (`:472`).
